# Plugin payload integrity

The omo-ai standalone edition ships a plugin payload at `<packageRoot>/plugin/`. This file tree is generated by `bun run build:omo-native` and is gitignored inside the install; only the build process knows its exact contents.

To make a tampered or corrupted payload fail closed at first launch, every published build now records the SHA256 of the staged payload in `plugin/.omo-payload.sha256`, format `"<sha256>  plugin\n"` (the same shape `sha256sum` writes). The launcher recomputes the hash on every cold start before it `execve`s the engine; if the recomputed hash does not match the marker, the launcher prints the re-install hint and exits 1 without spawning the engine.

## What is hashed

The manifest hashes only regular files (no symlinks) below the payload root, with the marker file itself excluded. The hash for each file is its raw content SHA256 written by `node:crypto` `createHash("sha256")`. The final payload hash is the SHA256 of the manifest string `path1\0hash1\npath2\0hash2\n...` joined in lexicographic order over POSIX-style relative paths. This is reproducible across filesystems and matches git's "tree object" determinism: two builds that produce the same set of files with the same contents produce the same hash, regardless of `mtime`, uid, or directory iteration order.

## When it is verified

The verification runs from `packages/omo-native/bin/lib/launcher.js`, immediately at the top of `runLauncher`, before any other command-parsing side effect (including `migrateLegacyBunGlobalManifest` and `reportLegacyFlatAdoption`). A failure aborts the launch before any engine file is loaded, before the doc directory or the agent settings are read. Every code path runs the verification first: `omo --version`, `omo setup`, `omo doctor`, `omo daemon ...`, `omo thread ...`, the interactive prompt, the standalone engine command passthrough.

The reinstall hint embedded in the message carries the package's `package.json` version, which is the version the user must reinstall to; a corrupt payload that cannot boot the engine still tells the user what to type.

## What it does not protect

- **The marker file itself** is content-addressed by the build, not the runtime: tampering with `.omo-payload.sha256` alone changes the expected hash but does not change the recomputed hash. The mismatch is detected.
- **Symlinks inside the payload** are skipped during the recompute. A user who adds a symlink under `plugin/` is asking for the engine to follow it; the integrity check does not gate that.
- **Hostile local user** (a user with write access to `plugin/`) can change both the payload and the marker; the integrity check protects against download-corruption, partial-write failures, and post-install tampering by other users on a shared box. It does not detect a process running as you that has already decided to ignore the launcher.

## What to do on refusal

When the launcher refuses to start, follow the hint in the message. The error reads:

```
Plugin payload integrity check failed: expected <hash>, got <other>. Please reinstall via `bun i -g omo-ai@<version>`.
```

For a corruption caused by an interrupted `bun i -g` or `npm i -g`, reinstalling with the same spec reproduces the published tree.

## CI artifact

The publish workflow records the per-version payload SHA256 as a workflow artifact named `omo-payload-sha256-<version>` (single line: the `<sha256>  plugin` marker payload). Use it to cross-reference a published payload against the install refusal you just observed: the expected hash printed in the launcher error must match the hash in the workflow artifact for the same `<version>`. A mismatch there is the published payload itself is corrupt; file an issue with both hashes.
