- A task's live status line keeps the thinking level after a runtime fallback (for example `openai-codex/gpt-5.6-sol:high`), taken from the level senpi applied on the switch, instead of dropping it. ([#7935](https://github.com/code-yeongyu/oh-my-openagent/pull/7935), fixes [#7934](https://github.com/code-yeongyu/oh-my-openagent/issues/7934))
- A delegated task's live progress line and its `/dag` node badge now name the model the child is actually on: after a fallback reverted the live line no longer kept naming the fallback model, and after an operator model switch neither kept naming the planned model. Every task label surface is now covered by one table test. ([#11904](https://github.com/code-yeongyu/oh-my-openagent/pull/11904), part of [#11359](https://github.com/code-yeongyu/oh-my-openagent/issues/11359))
- A delegated task whose model is not served by its route now moves on to the next model designated for it. When the provider answers that it does not serve the configured model (`model_not_found`, OpenAI's "The model `<id>` does not exist", `unknown provider for model`, Anthropic's `not_found_error` naming the model, or Google's `models/<id> is not found`), the next entry of the task's own category or agent chain takes over, a model on the same provider included. It never switches to the parent session's model or a default model. When no designated model is left, the task fails with `failure_kind: "model_chain_exhausted"` and lists each model with the reason `model not found`. ([#11355](https://github.com/code-yeongyu/oh-my-openagent/issues/11355))
- OpenCode runtime fallback hops when a provider failure arrives as `UnknownError`. `retry_on_errors` used to match only numeric HTTP codes, so an expired-auth or unexpected-server-error wrapped as `UnknownError` never switched models. The scoped classifier now treats those wrapped messages as retryable, so configured `models[]` still hop. Thanks @RaviTharuma. ([#11906](https://github.com/code-yeongyu/oh-my-openagent/pull/11906), fixes [#7702](https://github.com/code-yeongyu/oh-my-openagent/issues/7702))
- **A category or agent model change in omo.json applies to the next delegated task without restarting the session, and a broken omo.json stops the spawn instead of switching models.** The task engine reads omo.json once at every spawn, so an edited category chain or agent reaches the next child even while other children run and `/reload` is held. When an existing omo.json layer cannot be parsed or read, or any field that decides which model a child runs on is invalid anywhere it can be written (the user layer and every project layer; in each, the base config, its `[native]`/`[senpi]` block, and every profile and its `[native]`/`[senpi]` block, active or not; in each, category and agent `model`, `models`, `fallback_models` and reasoning selectors, and `exclude_models`), that spawn fails with an error naming the file and the position (`line:column`, or the JSON path of the field). Invalid means a wrong type, `null`, an empty value, or a model id that is neither `provider/model` (the legacy `model (high)` and `model high` suffixes still count) nor a catalog name the location can resolve. It never routes on the rest of the file, another layer, the built-in defaults or the session's startup config. A profile that is requested but does not exist keeps today's behaviour (the base config); an invalid field that does not route a Senpi child (for example `task.default_concurrency` or a `[codex]` block) is dropped with a warning, as before. Still read once at session start: the `task` settings (state dir, runners, residency), the plan-gate and DAG spawn policy, and the agent list in the task tool's description. ([#11358](https://github.com/code-yeongyu/oh-my-openagent/pull/11358), fixes [#11355](https://github.com/code-yeongyu/oh-my-openagent/issues/11355))
- **A delegated task that hits a usage limit no longer stays `running`, and an ambiguous limit no longer skips the rest of its provider's designated models.** A usage-limit turn settles after the engine's stated retry delay plus one heartbeat interval (10 s by default), unless the retry actually starts. A limit whose wording names neither a model family nor the account gets one try on the next designated model from the same provider, timed from its first provider request (60 s). A spent limit is remembered until the provider's stated reset (a failed or silent probe only for 30 minutes), so later tasks, resumes and revivals start on the first designated model that is still usable, or are refused with `failure_kind: "usage_limit"`. Every move stays inside the task's own designated model chain. When every designated model of one provider is spent, the task fails once as `model_chain_exhausted`, listing each model and its reason, including the ones it skipped. ([#11388](https://github.com/code-yeongyu/oh-my-openagent/pull/11388), fixes [#9711](https://github.com/code-yeongyu/oh-my-openagent/issues/9711), [#11383](https://github.com/code-yeongyu/oh-my-openagent/issues/11383))

## 2026-11-02 - model_not_found walks the designated chain per model (#11355); usage-limit turns settle in bounded time and an ambiguous limit is probed once inside the designated chain (#11388)

`credential-failure.ts` gains `isModelNotFound` (the senpi#4283 shapes). It outranks the credential and usage-limit classes, so `runtimeFallbackCandidates` keeps the whole remaining `fallback_models` (scoped to one model, like a model-scoped limit, never provider-wide even on a 401), and `terminalFailureMessage` adds no re-authentication hint. `ModelRefusalReason` gains `model_not_found` (label "model not found"), so each `model_refusals` entry and the `model_chain_exhausted` list name it.


`runners/rpc/turn-settlement.ts`: a held usage-limit error settles at its first confirmation (`settleConfirmMs` plus any stated retry delay from `auto_retry_start.delayMs`, the end's `delayMs` or Retry-After), whatever wake sources are live. An `agent_end { willRetry: true }` carrying a usage limit is held the same way, so a retry the engine announces but never starts still settles; a later terminal usage-limit end settles at once. A non-limit error held by a live wake source re-arms its confirmation instead of being dropped.

`manager/credential-failure.ts`: `usageLimitScope` returns `account` only when the text proves it (credits, balance, billing, a session window, the provider naming the account or organization) and `ambiguous` otherwise; senpi's "<provider> account usage limit has been reached" rewrite does not count as proof. `runtimeFallbackCandidates` drops the same-provider rungs on a confirmed account limit and keeps list order on an ambiguous one, so the next same-provider rung is tried once. It also skips rungs `manager/usage-limit-memory.ts` remembers as spent. Every candidate still comes from the record's own `fallback_models`.

`manager/usage-limit-memory.ts` remembers spent limits per provider (account) and per provider plus model family until `Resets at <ISO>`, else `LIMIT_MEMORY_DEFAULT_MS` (60 min). A failed or timed-out probe counts for `LIMIT_PROBE_FAILURE_MEMORY_MS` (30 min). Spawn, `respawn` and warm revival (`manager/usage-limit-revival.ts`) route along the designated chain around remembered limits, or refuse with `failure_kind: "usage_limit"`. `manager/usage-limit-probe.ts` bounds the probe rung by `limitProbeTimeoutMs` (`LIMIT_PROBE_TIMEOUT_MS`, 60 s) from `before_provider_request`, which `runners/probe-request.ts` signals for in-process and RPC children. A `child-unresponsive` probe outcome is walkable only for the task that is probing.

`manager/model-refusals.ts`: `terminalFailureFields` judges the spent chain with the same usage-limit memory the runtime walk used (passed through `OutcomeTrackerPorts.usageLimits`), so a chain the walk ended on a confirmed provider limit fails typed `model_chain_exhausted` instead of an untyped usage-limit stop, and every rung the walk skipped is listed with its reason.
