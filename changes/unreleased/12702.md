**Desktop memory sync now starts as soon as the engine boots, without waiting for a session.** An engine started by `omo host ensure` loads extensions only when a session opens, while the desktop opens none until the engine has sent the memory-sync bootstrap handshake, so the two waited on each other. The compiled `omo` and the npm launcher now start that one claim before the engine loads whenever an RPC engine's launch declares a `memory-sync` channel; the first session reuses it. A claim that fails still reports memory sync as unavailable and never falls back to CLI credentials. ([#12702](https://github.com/code-yeongyu/oh-my-openagent/issues/12702))

## 2026-11-07 - Claim memory sync when an RPC engine boots (#12702, part of #11997)

`bin/lib/memory-sync-boot.js` `claimsMemorySyncAtBoot` decides from the argv and the table's names only: `--mode rpc` before `--`, not an engine command, not the lifecycle supervisor, and a `SENPI_PRIVATE_FDS` object naming `memory-sync` (a table that does not parse leaves the claim to the extension). `compile-entry.ts` then runs `memory-sync-boot.ts` right before importing senpi's CLI, in both branches: senpi's `valid-cwd.js` and `private-fd-startup-release.js` first, in the CLI's own order, then omo-senpi's `desktop-sync/bootClaim.ts`, which captures the table and memoizes the process's one selection. The npm launcher sends such a launch through `bin/lib/engine-boot.js`, which drops itself from argv, runs the same steps with the device-account sidecar's `claimMemorySyncAtBoot`, and imports senpi's CLI in the same process (an exec argument such as a preload would make senpi respawn itself and lose the claimed descriptor). A failure at boot is one stderr line; the memory component's registration then selects as before. The npm `host ensure` hop that starts the engine is senpi's own CLI and is not covered here.
