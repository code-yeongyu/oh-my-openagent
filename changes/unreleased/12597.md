### Fixed

- Memory sync no longer loses an edit when two devices change the same line of a memory file at the same time. Devices on this version keep both edits as whole lines, and every device converges. Before, the edits were merged character by character into text that matched neither (#12279).
  - Between devices on this version, an edit does not disturb a line nobody edited. The exception is a very large rewrite: when one device adds and removes more than about 2,000 lines of a note in one save, that save is merged character by character, as before this fix, so a concurrent edit to the same line can still splice.
  - When the note's body or the new text does not end with a newline, the edit is still merged character by character, as before, so two concurrent edits to that last line can still splice.
  - With a device that still runs an older version, its old character merge can still go wrong in these ways:
    - **Adjacent lines can fuse.** The older device rewrites the line right after a line this version edited. Depending on the two devices' internal ids, the two edits can fuse into one line followed by an empty line. Measured: from `head`, `one`, `two`, `tail`, this version writes `ONE` and the older device writes `TWO`, and the result can be `head`, `TWOONE`, an empty line, `tail`. Two older devices give `head`, `ONE`, `TWO`, `tail`.
    - **Leftover text moves.** The older device edits a line this version deletes. Its leftover text joins a neighbouring line.
    - **Its own diff touches other lines.** The older device's character merge crosses into a line its user did not edit. This also happens between two older devices.
  - Two older devices keep their old character merge until they update.
- Memory sync: the push phase of a large memory set no longer needs memory in proportion to the whole set. Every push step used to re-read and re-write one journal file holding every pending item's data, several times per batch. A device pushing a few thousand memory files therefore peaked at 2 GiB or more (#12286). The journal now keeps a small index of pending items with their data in separate files, and a push reads only the batch it is sending. Capturing the set before the push still holds each captured file's text until the capture ends. A journal written by an older build is converted the first time it is read, including one where an older build added items next to the new index.
- Memory sync: a device receiving a large memory set no longer slows down with every file it lands. The render step used to re-read every render record of the cycle for each file, so the first pull of a few thousand memory files took tens of minutes (#12285). Each file now costs the same, and the crash-resume behavior is unchanged.
- Memory git no longer takes `core.hooksPath`, `core.fsmonitor`, `include.path` or `includeIf.*.path` from an inherited `GIT_CONFIG_COUNT` pair or `GIT_CONFIG_PARAMETERS` entry, so an exported pair such as `core.hooksPath=/dev/null` can no longer silently skip the memory repository's hooks and mirror push. Every other injected pair (`url.*.insteadOf`, `http.extraHeader`, credentials, `safe.directory`, ...) still applies, renumbered; an injected list git itself cannot parse is dropped whole. Memory git also no longer inherits repository redirection (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_NAMESPACE`, `GIT_CONFIG`, ...), so it can no longer be pointed at another repository; `GIT_INDEX_FILE`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` are kept. ([#12360](https://github.com/code-yeongyu/oh-my-openagent/pull/12360), fixes [#12354](https://github.com/code-yeongyu/oh-my-openagent/issues/12354))
