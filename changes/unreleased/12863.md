**An agent that messages a session on another device now always gets an answer back, without a monitor.** When the receiving session's run settles, its final answer is delivered into the sender's session as a message from another agent (naming the device, the session and the message it answers), and the sender picks it up the way it picks up a message from a session on the same device. When a local user or another agent also wrote to the receiving session in that same run, the answer starts with a line saying it may include content from that other input. A reply held because the sender's user is typing a draft is retried until it is admitted. The receiving device delivers the answer only to engines that can admit it as an agent message; an older engine is reported in the log by name instead of being sent a plain prompt. ## 2026-11-08 - A cross-device peer send is answered back into the sender's session (#12863, part of #12852)

`thread/remote/remote-ops.ts` `promptRemote` stamps a peer send with a reply route as senpi's `clientMessageId` (`remote/reply-route.ts` `replyRouteToken`: `omo-peer.v1:` + base64url of a versioned binary record of the sending device, session, delivery id, root and hop, with lowercase-UUID ids as their 16 bytes, about 115 characters for four UUIDs; refused `invalid_arguments` before sending when it would pass 256 characters). `remote/lazy-ops.ts` `wireReplyRoutes` (registered by `component.ts`) runs `createReplyRouter` over the session's own `message_start` / `message_end` / `tool_execution_end` / `agent_settled` / `session_shutdown` events. Every routed user message the run consumed gets the run's final answer (its last assistant text without a tool call, else its last text) at `agent_settled` (Q ruling 2026-11-08: no per-input attribution, and nothing in this path ends with the sender receiving nothing). Only user messages and `session_control_delivery` count as inputs; when the run had more than one, `remote/reply-admit.ts` `admitReplyRemote` puts `OTHER_INPUT_LABEL` under the body's first line `Reply to delivery <id>.`. Engine and extension customs (turn-start context, the memory recall, continuations, task completions, omo's idle wake) never count. The reply is senpi#6233 `admit_external_message` with `deliveryId: reply-<delivery>`, an `agent` sender claim, `deliverAs: followUp` and `chainCount: hop + 1`, so it is never a user prompt and never expands a slash command; A's engine starts a turn on it when idle. A run that already reached the sender's session with its own `thread_send` sends no automatic reply. A refusal or disposition `held_draft` is `{ kind: "held" }`: B logs `remote_reply_held` and retries with the same delivery id on a backoff of about half an hour (`heldRetryDelaysMs`), then logs `remote_reply_failed`; the retry timers are unref'd and cleared at `session_shutdown`. An engine without the record (`ADMIT_UNSUPPORTED` refusals) is logged as `remote_reply_unavailable`. Each delivery is answered at most once per session lifetime (the last 256 delivery ids are kept).
