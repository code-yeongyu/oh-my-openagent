**An agent that messages a session on another device now gets the answer back without asking for it.** When the receiving session's run answers the message, that answer (and only that answer, never one the session gave its own user or another agent in the same run) is delivered into the sender's session as a message from another agent, and the sender picks it up the way it picks up a message from a session on the same device. No monitor is needed. The receiving device delivers the answer only to engines that can admit it as an agent message; an older engine is reported in the log by name instead of being sent a plain prompt. ([#12863](https://github.com/code-yeongyu/oh-my-openagent/pull/12863), part of [#12852](https://github.com/code-yeongyu/oh-my-openagent/issues/12852))

## 2026-11-08 - A cross-device peer send is answered back into the sender's session (#12863, part of #12852)

`thread/remote/remote-ops.ts` `promptRemote` stamps a peer send with a reply route as senpi's `clientMessageId` (`remote/reply-route.ts` `replyRouteToken`: `omo-peer.v1:` + base64url of a versioned binary record of the sending device, session, delivery id, root and hop, with lowercase-UUID ids as their 16 bytes, about 115 characters for four UUIDs; refused `invalid_arguments` before sending when it would pass 256 characters). `remote/lazy-ops.ts` `wireReplyRoutes` (registered by `component.ts`) runs `createReplyRouter` over the session's own `message_start` / `message_end` / `tool_execution_end` / `agent_settled` / `session_shutdown` events. The router splits the run at each input: a user message or any custom message (another party's `session_control_delivery`, a ulw-loop continuation, a task completion), except the memory recall (`omo-kibitzer:recall`), which is context the session gives itself. A route gets the last assistant text given before the run's next input, so output that followed the local user's input or another peer's input never goes to it. A route whose input shares an answer with another input is logged as `remote_reply_skipped` and nothing is sent. That is the case when another input arrives before the route's final answer (an assistant message that calls no tool), or when the route steers into a run whose earlier input has no final answer yet. At `agent_settled` each route goes back, one at a time in settle order, through `remote/reply-admit.ts` `admitReplyRemote`: senpi#6233 `admit_external_message` to the located sender session, with `deliveryId` `reply-<delivery>`, `sender: { kind: "agent" }` only, `deliverAs: "followUp"`, `chainCount` = hop + 1, and the #12858 peer text with the answer capped at `THREAD_MESSAGE_MAX_BYTES`. A refusal meaning the record is missing on the other side (`method_unclassified`, `delegation_unclassified`, `unknown_command` and kin) is logged as `remote_reply_unavailable`, and no prompt is sent instead; other failures, including a settle that names no session id, are logged as `remote_reply_failed`. Each delivery is answered once per session (a bounded routed list), a reply carries no route, and a route whose own segment made a successful `thread_send` that reached the sender (by id, name or alias: its result's resolved `thread_id`, compared with the sender's durable id and its located listing key) is not answered again. A run woken by a cross-device input (an admitted delivery's `chain_count`, or a routed prompt's hop) continues that chain in its next cross-device send (`tools/ports.ts` `callerChainHop`, read by `tools.ts` `remotePeer`), so `threads.chainCountLimit` bounds a cross-device loop.
