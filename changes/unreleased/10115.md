### Fixed

- A facts entry too large for an ordinary batch now runs on the first model in your facts chain whose context fits it, instead of being parked because the first model in the chain was too small. The resolved model is tried first, then its declared fallbacks in order; built-in or registry models are never used. The run is otherwise unchanged: one model, no fallback rungs, nothing split or truncated. An entry that no declared model fits is parked as before. ## 2026-11-13 - Oversized facts entries run on the first declared model that fits (#10115)

`memory/facts-runner.ts`: `oversizedFactsCandidates()` resolves the declared facts candidates (the resolved model, then `resolution.fallbacks`) against the child model registry, and admission walks them in order, pinning each oversized entry to the first candidate whose known `contextWindow` fits it under `admitOversizedFacts`. `pinFactsResolution()` launches the oversized run on that candidate with its own thinking and no fallbacks; an entry no candidate fits is classified `payload_entry_oversize` as before. Ordinary batches are unchanged.
