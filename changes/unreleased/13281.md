**Plain `omo login` signs a computer in from the terminal while OmO accounts are closed.** A computer with no OmO desktop app — a server over SSH, a fresh Linux box — runs `omo login`, gets a device code to approve on another device, and stores the credential in the OS credential store; the attach-before-mint refusal (#13096) answers a computer that already has its device before anything is asked of the service. The success line names the signed-in account (`Signed in to OmO as <email>.`), and `omo whoami` names it too; a failed account read still says how to see it. `omo logout` and `omo whoami` run while closed, so no message names a command that refuses. `login --help` describes the route (the command stays hidden from `omo --help`), every other closed `login` form refuses with a message that names the route, the closed hints name both routes, and the compiled entry classifies bare `login`, `logout` and `whoami` as one-shot launches with the same shared parse the command uses (`login --` included). The damaged-item message names the terminal route too instead of a desktop-app-only dead end. Tests run the flow through the npm launcher (against a service-auth bundle built from this source into a temp copy of the launcher tree), the compiled entry and the toolkit CLI, with an isolated HOME and runtime dir, no inherited session bus, an injected store, and a refusal-text assertion on every zero-mint case.
