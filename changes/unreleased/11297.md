**A session command OmO adds later is no longer sent to an attach-enforcing senpi host without an attachment.** The thread client fenced only a fixed list of mutations, while the host refuses every session command from an unattached connection except its read allowlist; under `SENPI_RPC_REQUIRE_ATTACH=1` any command missing from the client's list would be refused. The client now fences every session command except the reads the host exempts. ([#11278](https://github.com/code-yeongyu/oh-my-openagent/pull/11278), part of [#10944](https://github.com/code-yeongyu/oh-my-openagent/issues/10944))

**A summary queued by a session that named only its profile is judged with the account's home again.** Since #11202 a queued session summary is judged by the config it was recorded under; when that config named a profile but no home, the consent read had no home at all and fell back to the working directory. It now reads the account's home, as the send gate does. The reference doc also says that summaries queued before #11202 keep the old reading until they expire. ([#11275](https://github.com/code-yeongyu/oh-my-openagent/pull/11275))

**Memory sync and the `memory` tool no longer hang while a macOS keychain approval dialog is open.** A session's sign-in read now gives up after 5 s with an error that names the "bun wants to access key omo-cli" dialog to answer, instead of waiting with no end. Memory sync skips that pass, logs why, and retries after 15 s, doubling to a 5-minute cap, and the `memory` tool returns at once. A one-time "Allow" clicked after that 5 s deadline is not kept, so the next sync retry asks again; choose "Always Allow" to stop the prompts. All reads in one process share the one keychain request that is still waiting, so parallel sessions no longer stack a blocked read (and another dialog) per request, and after a late approval the next read goes back to the OS store, so another process's rotated token cannot be replaced by an old answer. `omo login`, `omo whoami`, `omo account` and `omo sync` still wait for the dialog, and now say so after 2 s. Reported by @floweredao. ([#11264](https://github.com/code-yeongyu/oh-my-openagent/pull/11264), part of [#11262](https://github.com/code-yeongyu/oh-my-openagent/issues/11262))

## 2026-10-25 - memory sync defers a pass while the keychain waits for approval (#11264)

`device-session/account-source.ts` turns the credential store's `KeychainApprovalPendingError` (a session read past its 5 s deadline in `service-auth/keystore.ts`) into `SyncSessionDeferredError` (`sync-session-deferred.ts`, matched by its code because the account sidecar carries its own copy of the class), and `signedOut()` answers false while the keychain waits, so a pending keychain never reads as signed out. `sync-runner.ts` logs the store's message, leaves the repo idle (status `null`, so the `memory` tool's status read returns at once), and launches the pass again after `deferredRetryMs` (15 s initially, doubling to a 5-minute cap, with one warning per escalation) while the same sessions still hold the repo.

Settled answers are never cached. A write or clear invalidates the pending-read entry, and an old read settling afterward cannot restore it. Native writes retain their existing unbounded behavior; safe write deadlines need the single credential-owner design tracked in #11262.

Must not break: a retry joins the process's one parked keychain read instead of starting another, so it adds no prompt; a pass that resolves the session normally schedules no retry.
