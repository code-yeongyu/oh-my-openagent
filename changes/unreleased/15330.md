### Changed

- `task_send` now resolves a task among the calling session's own tasks (the task's parent or root session), as `task_cancel` does. Without `all_scope`, a task of another session reads as not found, by id and by name, where it used to answer with a refusal; `all_scope: true` still reaches every session's task. A re-dispatch follows the same rule (#15330).

## 2026-11-27 - task_send resolves in the caller's scope (#15330)

`sendToTask` and `redispatchTask` resolve their target through `resolveSendTarget` (`steering/scope-resolver.ts`): with a caller session, only that session's tasks (parent or root) unless `allScope`, which tries the caller's own first and then any session; without a caller, an id, else the first record carrying the name. What does not resolve gets the existing not-found answer (`sendNotFound` / `redispatchNotFound` in `steering/engine-policy.ts`), so the `scope_denied` kind is removed from `SendOutcome` and `RedispatchOutcome` and from every switch over them. The `task_send` tool passes the calling session and `all_scope` as one scope; a call without a caller session reaches a task only with `all_scope`. The manager's checks before an explicit send (`manager/explicit-send.ts`) resolve through the same function, so an outside task is answered before the owner's decision or a refused stop's wait is asked. A workflow node send names the run's own session with `allScope`; an eval handle names its owning session.
