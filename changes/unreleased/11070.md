**`omo update` on the release binary now installs the update.** It used to only print a curl-and-mv command, although `omo update --help` says only `--dry-run` / `--print` print. It now downloads the release asset, checks it against the release's published SHA-256 before writing or running it, confirms the download reports the target version, and swaps it in by rename, keeping the binary's file mode; `--dry-run` and `--print` still only print. If the directory is not writable, or the download, checksum, version check or swap fails, the installed binary is left in place (on Windows a failed swap puts the previous binary back), and the command exits 1 with the reason and the manual command. Package-manager installs are still refused as before. ([#11070](https://github.com/code-yeongyu/oh-my-openagent/pull/11070))

**`omo update` on a standalone install replaces the omo you installed again.** Since 5.1.56 it printed (and, with this change, would have installed) the release over omo's runtime copy under `~/.omo/binary-runtime/<version>/`, so the update never applied and "Update Available" stayed. It now targets the binary you launched, falls back to the `binPath` the installer recorded in `~/.omo/install.json`, and refuses with exit 1 when it can find neither, rather than touch the runtime copy. ([#12168](https://github.com/code-yeongyu/oh-my-openagent/issues/12168))

**On Windows, `omo update` no longer fails because a file is held open.** If the `omo.exe.old` left by the previous update still belongs to a running omo, the binary being replaced moves to a fresh `omo.exe.old-<id>` name instead, and a rename refused because a scanner briefly holds the file is retried for up to about 8 seconds before the update gives up and restores the previous binary. ([#10343](https://github.com/code-yeongyu/oh-my-openagent/issues/10343))

## 2026-11-02 - Compiled omo update installs the release (fixes #11062)

`compiledUpdate` takes a `replaceBinary` seam; the compiled entry passes `downloadAndSwapBinary` from `compiled-update-swap.ts`. `swapReleaseBinary` refuses an unwritable directory first, then downloads `SHA256SUMS` and the asset into memory and compares the asset's sha256 before anything touches the disk, writes it under a random `<binary>.new-<hex>` name with the installed binary's mode, runs its `--version` (dropping an inherited `BUN_BE_BUN`) and renames it over the binary; on win32 the old binary moves to `.old` first and is renamed back when the second rename fails. The platform steps are injected (`SwapSteps`), so the win32 branch and its rollback run under test on every OS. Probe output echoed in an error is one line of at most 200 printable characters. Must not break: nothing is written or executed before the checksum matches, and `--dry-run` / `--print` / the package-manager refusal still never install.

The update target (fixes #12168): since #10762 the launcher's trust stage re-execs the provisioned runtime, so `omo update` runs inside `~/.omo/binary-runtime/<version>/omo` and `runningExecutablePath()` names that copy. `handOffToProvisionedRuntime` now also sets `OMO_PROVISIONED_LAUNCHER` to the launching executable; `planProvisionedLaunch` reads it only together with a matching `OMO_PROVISIONED_HANDOFF` and always deletes it, so it never reaches the engine. `updateDestination` picks the launcher, then a standalone `install.json` `binPath` (absolute, an existing file, outside the runtime root), else the running executable; `compiledUpdate` refuses any destination inside `runtimeRoot` before the release lookup, the print and the install.

Windows locks (relates #10343): `swapReleaseBinary` frees `<binary>.old` with `steps.remove` and, when that throws (the image of a still-running omo), moves the binary to `steps.asidePath` (`<binary>.old-<hex>`) instead. Each win32 rename, including the rollback, retries an `EBUSY`/`EPERM`/`EACCES` refusal after 250, 500, 1000, 2000 and 4000 ms (`steps.pause`); any other error is not retried. `planProvisionedLaunch` trusts `OMO_PROVISIONED_LAUNCHER` only when it is an absolute path.
