### Fixed

- **A delegated task that hits a usage limit no longer stays `running`, and an ambiguous limit no longer skips the rest of its provider's designated models.** A usage-limit turn settles after the engine's stated retry delay plus one heartbeat interval (10 s by default), unless the retry actually starts. A limit whose wording names neither a model family nor the account gets one try on the next designated model from the same provider, timed from its first provider request (60 s). A spent limit is remembered until the provider's stated reset (a failed or silent probe only for 30 minutes), so later tasks, resumes and revivals start on the first designated model that is still usable, or are refused with `failure_kind: "usage_limit"`. Every move stays inside the task's own designated model chain. ([#11388](https://github.com/code-yeongyu/oh-my-openagent/pull/11388), fixes [#9711](https://github.com/code-yeongyu/oh-my-openagent/issues/9711), [#11383](https://github.com/code-yeongyu/oh-my-openagent/issues/11383))

## 2026-11-02 - Usage-limit turns settle in bounded time; an ambiguous limit is probed once inside the designated chain (#11388)

`runners/rpc/turn-settlement.ts`: a held usage-limit error settles at its first confirmation (`settleConfirmMs` plus any stated retry delay from `auto_retry_start.delayMs`, the end's `delayMs` or Retry-After), whatever wake sources are live. An `agent_end { willRetry: true }` carrying a usage limit is held the same way, so a retry the engine announces but never starts still settles; a later terminal usage-limit end settles at once. A non-limit error held by a live wake source re-arms its confirmation instead of being dropped.

`manager/credential-failure.ts`: `usageLimitScope` returns `account` only when the text proves it (credits, balance, billing, a session window, the provider naming the account or organization) and `ambiguous` otherwise; senpi's "<provider> account usage limit has been reached" rewrite does not count as proof. `runtimeFallbackCandidates` drops the same-provider rungs on a confirmed account limit and keeps list order on an ambiguous one, so the next same-provider rung is tried once. It also skips rungs `manager/usage-limit-memory.ts` remembers as spent. Every candidate still comes from the record's own `fallback_models`.

`manager/usage-limit-memory.ts` remembers spent limits per provider (account) and per provider plus model family until `Resets at <ISO>`, else `LIMIT_MEMORY_DEFAULT_MS` (60 min). A failed or timed-out probe counts for `LIMIT_PROBE_FAILURE_MEMORY_MS` (30 min). Spawn, `respawn` and warm revival (`manager/usage-limit-revival.ts`) route along the designated chain around remembered limits, or refuse with `failure_kind: "usage_limit"`. `manager/usage-limit-probe.ts` bounds the probe rung by `limitProbeTimeoutMs` (`LIMIT_PROBE_TIMEOUT_MS`, 60 s) from `before_provider_request`, which `runners/probe-request.ts` signals for in-process and RPC children. A `child-unresponsive` probe outcome is walkable only for the task that is probing.
