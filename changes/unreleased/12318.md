### Fixed

- Input sent over a session's RPC socket (`prompt`, `steer` or `follow_up`) now counts as typed input for the thread tools. A run it starts or joins never claims the input as a delivery it received: when the client reused the id of a real delivery that this session never received, `thread_send` was refused `invalid_arguments` (`guard: "unknown_cause"`) or continued a chain the session was not part of. Such a send now starts a new causal chain, and a run the gateway started from a bound thread keeps that thread's chain (#12317).

## 2026-11-04 - RPC input is typed input to the thread tools, never a received delivery (#12318)

`thread/component.ts` `deliveryOf` recognises RPC input by the sender senpi stamps on it (`{ kind: "external", platform: "rpc" }`, `session-control-input-commands.js`); senpi admits RPC `prompt`/`steer`/`follow_up` input as a `session_control_delivery` message under the client's `clientMessageId`. `noteInput` treats that input as typed input (`local`) and never takes it as the run's causal `cause`, a `consumed` origin or a reply sender. dev already starts a new root for a cause no row holds (`store-ops.ts` `placeCausally`), so a bare `tui-rpc-*` id was not refused; what this adds is that a client-chosen id equal to a real delivery is never claimed, and an RPC steer in a gateway-started run does not replace its cause. A sender stamped this way on a relayed delivery only loses the delivery's privileges, never gains any. Tests: `report-origin.test.ts` "input sent over the session's RPC socket (#12317)" (the A-chain steer and the reused-id cases are RED on dev); its delivery message now carries the admission's sender as senpi's does.
