**macOS computer use keeps the display awake while it operates, and says when the screen is locked or asleep.** The engine now holds a `PreventUserIdleDisplaySleep` power assertion ("OmO computer use is operating the desktop" in `pmset -g assertions`) from the first request other than `capabilities`, `control.state` and `stopPath.*` until 60 seconds after the last one; `session.close`, a disconnect and a stop release it at once. `capabilities.displayAsleep` reports when every display of the session sleeps, `omo doctor` prints it on the display line, and a `CaptureFailed`, `InputFailed` or `Timeout` message ends with `(the screen is locked)` or `(the display is asleep)` when that is the likely cause. Other platforms are unchanged. ([#11530](https://github.com/code-yeongyu/oh-my-openagent/pull/11530), part of [#11466](https://github.com/code-yeongyu/oh-my-openagent/issues/11466))

### Fixed

- Computer use on macOS: a background left-button drag or `holdMouse` now runs only from a control that tracks the drag itself (a slider, scroll bar, splitter or stepper); anywhere else, or when the start point cannot be read, it reports `BackgroundUnavailable` before sending anything, because a press on an item can begin a drag-and-drop session that macOS completes from the user's real pointer. A background drag whose source still begins such a session is taken back to its start and released there, or reported with its drop unconfirmed, as `InputFailed`. ([#11726](https://github.com/code-yeongyu/oh-my-openagent/pull/11726), part of [#11464](https://github.com/code-yeongyu/oh-my-openagent/issues/11464))

### Added

- Computer use on macOS: `click`, `el.click`, `el.press` and `el.perform` take a `menu` option, the path of item labels to choose in the menu the press opens (a right-click's context menu, or the menu of a menu button or popup button). The item is chosen in the same call and the menu is closed before the call returns, chosen or not, so a menu opened in a background application never keeps the user's keyboard. A path that matches nothing, a disabled item, or a press that opened no menu reports `InputFailed` naming the menu's items. ([#11723](https://github.com/code-yeongyu/oh-my-openagent/pull/11723), part of [#11464](https://github.com/code-yeongyu/oh-my-openagent/issues/11464))
- Computer use on macOS: `el.selectText(text, { prefix?, suffix?, select? })` selects a text range inside one accessibility element's value without moving your focus, sending a key or changing the value; the match must be unique (prefix and suffix disambiguate it, an ambiguous match is refused with nothing selected), `select: "start" | "end"` places a caret instead, and the reply names the applied selection so a following `el.type()` replaces exactly it. ([#11715](https://github.com/code-yeongyu/oh-my-openagent/pull/11715), part of [#11462](https://github.com/code-yeongyu/oh-my-openagent/issues/11462))
- Computer use (macOS): `win.bringToCurrentSpace()` moves a window that sits on another Space (a Mission Control desktop) into the Space you are using, without activating it or switching Spaces; a window already there is left alone. Like upstream oh-my-pi it needs no foreground-control grant, and it is audited like every other input. It refuses with `SpaceMoveDenied` before moving anything when your current Space is a fullscreen app's, and also when macOS will not move the window or your Space or focus changed meanwhile; other platforms, and macOS versions without the needed window-server functions, refuse with `SpaceUnsupported`. The engine method is `window.bringToCurrentSpace`. ([#11517](https://github.com/code-yeongyu/oh-my-openagent/pull/11517), part of [#11463](https://github.com/code-yeongyu/oh-my-openagent/issues/11463))
