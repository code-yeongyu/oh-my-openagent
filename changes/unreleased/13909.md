**Computer use v3 on Wayland: input over libei.** Wayland desktops take keyboard and pointer input through libei, either over the RemoteDesktop portal or a `LIBEI_SOCKET`. A dropped connection is retried a bounded number of times instead of failing the next call, and a lost portal session never raises a new consent dialog on its own. Keys resolve through the keymap the compositor sends, in the active layout only; a character that layout cannot type is refused with a pointer to paste. Input outside every screen region is refused before anything is sent. Until a compositor is measured to release held keys when the engine dies, holding a key or button is refused there, while ordinary presses still work. Paste never falls back to typing when no clipboard route exists. ([#13909](https://github.com/code-yeongyu/oh-my-openagent/pull/13909))

## 2026-11-16 - v3 Wayland input over libei (#13909)

`omo-computer-backend-wayland`: `input/` owns the libei link (socket route or one combined RemoteDesktop portal session, 3 bounded reconnect attempts at 250/500/1000 ms, a second `ConnectToEIS` on a live portal session, else `libei_lost`), the CLOEXEC EIS descriptor, region preflight and event emission; `xkb/` resolves characters through the compositor-fed keymap with libxkbcommon loaded at runtime. `ledger.rs` + `release.rs` read SP-W's release-on-close row and gate holding verbs (`wayland_release_unproven`, `ax_only` on a contradicted row); `consent.rs` asks again per engine lifecycle; `clipboard.rs` is the data-control -> portal Clipboard -> none ladder; `fake/` (feature `fake`) is the scripted EIS server and portal, also shipped as the `omo-fake-eis` example for the Linux QA driver's new `sway` and `weston` sessions. Core gains reason `libei_lost`; the engine routes `OMO_COMPUTER_BACKEND=wayland`; the session refuses `key.down` / `mouse.down` while `releaseHelper` is unavailable.
