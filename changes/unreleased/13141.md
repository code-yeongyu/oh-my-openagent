**A fuzzy handoff no longer fails on an account with many ended sessions, and never goes to a different session than an exact name would.** A fuzzy handoff first tries the thread's exact id, alias or name across every session, ended ones on other devices included, so a name that exactly matches one session always reaches that session. Otherwise local, live and ended sessions are compared together and the clearly best match wins wherever it lives; two equally good matches ask you to pick. Ended sessions that cannot match no longer count against the 500-candidate fuzzy cap, so a large history no longer blocks a unique match. ([#13141](https://github.com/code-yeongyu/oh-my-openagent/pull/13141), follows #13066)

**A thread whose alias claim asks for a sign-in after it was created is still named by the alias.** When the account token expires between `thread_create` checking an alias and claiming it, the thread it already created is now named by the alias on its device and the call answers `ok` with `alias_scope: "local"`, instead of an error. `thread_rename` does the same when the account is gone by the claim. An alias used as a local name is now trimmed on every path. ([#13179](https://github.com/code-yeongyu/oh-my-openagent/pull/13179), follows #13112)

**`omo login` no longer registers a second device for a computer that already has one.** Before any code, browser tab or new key, it checks the stored sign-in and the device the computer's OmO device service holds (parked included). A held, uncertain, locked or unreadable state refuses a new device and keeps the existing one, instead of adding an "omo CLI on <host>" row beside the desktop's. When the service advertises machine identity, both sign-in flows send a hashed hardware id (`SHA256("omo-machine-v1" + id)`; the raw id never leaves the computer), and a `machine_exists` refusal ends the sign-in without removing or taking over any device. ([#13096](https://github.com/code-yeongyu/oh-my-openagent/pull/13096))

## 2026-11-12 - A fuzzy handoff resolves exact names first and ranks ended remote rows with every other candidate (#13141, follows #13066)

`tools/internals.ts` `resolveAcross`: for `match: "fuzzy"` the exact ladder (`resolveTarget`: id, alias, name) runs first over local entries plus every account row, ended ones included, and its hit is the answer unless it is the caller. Otherwise `fuzzyMatch` ranks one set: local entries, the account's live rows and the ended rows `fuzzyContenders` (`addressing.ts`) keeps, those scoring at least the accept floor minus the margin (0.64), the only ones that can lead or block a leader. The 500-candidate cap applies to that set. Review fix at 54e5b128ab: ended rows were compared only when local plus live answered `not_found`, so a live row at or above 0.72 beat an ended row that matched better or exactly ("release planner" went to the live "release planner notes", while exact reached the ended "release planner"). Tests (`remote/route-parity.test.ts`): "600 ended remote rows + unique local" (non-contending ended rows stay out of the cap), "live remote exact title beats a local near-match", "only an ended remote row matches" (fuzzy and exact reach it through the same relay calls), "an ended row named exactly as the query and a live near-match" (RED at 54e5b128ab: sent to dur-on-b; fuzzy and exact relay calls now `toStrictEqual`), unequal scores in both directions (RED at 54e5b128ab for the better ended row), "a live and an ended row match equally" now `ambiguous_target` with no send (54e5b128ab sent to the live row; the exact path refuses two rows sharing a name), and exact/fuzzy parity on a local exact name with a remote near-match.
