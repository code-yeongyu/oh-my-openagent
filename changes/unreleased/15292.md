### Fixed

- A workflow run whose host process was killed (a crash, a reboot, a terminal restart) no longer stays shown as running after the session reopens. The reopened session takes the run over: a child that is still alive is reattached, a finished one is folded, one that died with its host fails its node, dependents start, and the parent is woken when the run settles (#15125).
- A session never takes over, pauses, stops, retries or cancels a workflow run that another live process is still running (including one still shutting down; a user Stop leaves such a run running and logs a warning naming its holder), cancelling a run that lost its scheduler really stops its node children, closing a session while it is still taking a run over leaves that run paused with no later takeover, and a cancel that arrives while the session is still taking a run over (or reviving it with a retry or an amend) waits for it and then really cancels it; a retry, send, amend, guidance or node cancel that arrives meanwhile is refused as busy and can be repeated (#15125).
- Sending a message that revives a finished node of a failed workflow run now takes that run over for this session until the revived node finishes: another process can no longer retry, amend or revive the same run in the meantime (it is told the run is held by a live process), and a revive refused by the task is undone without leaving the run held (#15125).
- A retry or amend of a workflow run is refused ("still runs <node>") while a node revived by a send is still running, and works once that node finishes; a revived node keeps the run held even when recording the revive fails. If the scheduler driving a run fails inside a live session, that session picks the run up again as soon as no other operation is using it, instead of leaving it shown as running until the next session start; if it fails again, the run is parked with its children stopped and its nodes failed with the real error, and it can be cancelled or retried (#15125).
- Automatic recovery never resumes a run the user stopped, even when the Stop lands while recovery is already looking at the run; a Resume resumes exactly the Stop it was issued for (#15125).
- Cancelling a workflow run stops every child the run owns, including a finished node's child that resumed on its own and a child of a node an amendment removed. A child whose stop is not confirmed yet still counts as running.
- While a cancelled or settled run still owns a running child, the run reports that its stop is owed, in the tool and the status widget. Until a repeated cancel finishes the job, the run refuses to be amended, retried, sent to or re-entered.
- A finished child that starts work on its own after its node moved to a newer attempt, its node was removed, or its run is being cancelled or has ended, is stopped. A child of a failed or completed run keeps answering an explicit send.
- A message sent with task_send to a workflow child that is no longer its node's current attempt, whose node was removed, or whose run was cancelled is now refused with what to do instead (retry the node), and the child is not revived. Addressing the child by name waits for its pending stop exactly as addressing it by id does.
- A re-run, retried, amended, recovered or messaged node never adopts, reuses, revives or runs beside a child left over from an earlier attempt (#11381, #9993).
- Cancelling a failed workflow run while one of its nodes is revived by a message now stops that revived child. The run stays failed, and the node records how the child ended.
- While you have stopped a workflow run, a finished node whose child starts work on its own is held instead of running. The node shows that a trigger was held (how often, first and last time); sending to the node continues it. Resume shows the record but does not continue the child by itself.
- In a large workflow run, children that finish while later nodes are still being admitted are folded right away, and their dependents start, where finished children used to stay shown as running until the whole admission batch ended (#10057).
- A workflow node whose child finishes and then resumes on its own is followed again: the node returns to running and folds the resumed turn's outcome, where the run used to keep the first result and ignore the rest (#12134). Cancelling the workflow also cancels such a resumed child, including one that wakes while the cancel is under way (even after an earlier cancel found it finished) or that resumed while the session was restarting. A resumed turn that already ended while the session was down is folded when the workflow is recovered, instead of the workflow continuing on the earlier result. A node that was waiting for a free child slot does not start on the earlier result: it waits for the resumed turn and is skipped if that turn fails.
- A subagent whose turn ends on a provider usage limit no longer stays shown as running: the turn settles in bounded time, the next model of its chain is tried, and when the chain is spent the child ends with an error the parent receives. A limit whose scope is unclear is probed once instead of being treated as account-wide (#9711).
- A child task whose turn ends while its own background work is still running (a detached eval cell, a background command, a monitor, its own children) is no longer recorded as completed with its progress note as the result: the turn is held until the turn that work wakes answers. Work that ends without waking the child, or that stays silent for an hour, ends the task as `async_work_pending`, never with the progress note. This also holds when the session ends before the turn's idle edge, and after the parent restarts, restores an in-process child, or the host reopens the child's session from its file (#10487). Cancelling a workflow or a task whose child is waiting for its own background work ends that child at once; no later turn runs. A workflow cancel marks every child cancelled at once; an in-process child that is mid-turn finishes its current turn before it stops (#15191).
- A background child no longer stays shown as running forever after a follow-up it refused: the finished run is restored when a warm revival prompt is refused, while a stop accepted meanwhile still ends it cancelled and messages queued meanwhile are kept. A reused process id is no longer mistaken for the child's live owner, a workflow run is no longer treated as held by another process when that process id was reused by an unrelated program, a child its own run paused reads as paused instead of held by another host, a paused orphan is parked for its run instead of being disposed or marked lost by any startup sweep, and a session that stops while a child's owner is being checked no longer has that child revived (#12077, #12080).
- After a session reopens, a workflow node whose child could not be revived at once - no free child slot yet, or its task host not answering yet - no longer fails as orphaned while the child is about to come back. The node waits for the revival (the workflow view says it is waiting for its child to be revived), including the last revival attempt made when the waiting time runs out, follows the child once it runs and folds its result; only when the revival is given up does the node fail with that reason, and the run then retries it with a fresh child like any task its host could not keep. A child nothing will revive still fails at once, and closing the session never marks a waiting node failed (#15150).

## 2026-11-27 - One acquisition decides who takes a DAG run (#15125)

A host that dies without writing the shutdown pause leaves its DAG run `running`; recovery now claims such a run, like a paused one, once its holder is gone. Every entry that schedules or mutates a run takes it through `acquireDagRun` (`run-acquisition.ts`): under the run lock, on the fresh checkpoint, it checks the entry's eligibility (one named predicate per entry in `dagRunEligibility`: `freshStart`, `reentry`, `automaticRecovery`, `forkSourceAdoption`, `userResume`, `unheldCancel`, `shutdownPause`, `userStop`, `send`, `stoppedWrite`), asks the one holder rule (`runHolder` / `liveForeignHolder`: lease, then previous holder, then the live owner of an active child), takes this process's per-run reservation (`createDagRunReservations`; a reservation it created is released if its own lease write fails) and writes the lease, and returns the exact record acquired. The entry decides and writes from that record: `acquireReentryLease` returns it, and retry and re-entry validate their targets, status and capacity on it. `decideDagRun` is the same decision without taking anything; the user Stop and the user-stopped-run controls evaluate their rule inside their journal's locked append (`controlJournal`'s `skip`). The lease leaves the record only in the write that ends this host's holding (`leaseAfterEvent`: terminal, park, user Stop, the fold of the last revived node of a settled run; the shutdown pause hands it over as `previousLeaseHolderPid`). Changed behaviour: a send is decided once under one run lock into guidance, steer, revive or a typed refusal (`classifySend`, `leaseWhen`); a revive of a child of a `failed` run takes the run (lease) before it touches the child, and the run stays held until the fold of the last revive, counting revive-sends still in flight (the fold waits for the run's reservation). Every write to a user-stopped run is decided at the write by the same Stop and the holder rule (`appendWhileStopped`), and an amendment of a paused run (a user-stopped one included) is decided at its write by the same holder rule, passed in by the caller (`DagAmendParams.holder`; the lease-only `liveLeaseHolder` check is gone). The reservation registry moved to `run-reservations.ts`. A reserved run refuses verbs with the retryable `run_busy`. A scheduler that finds active nodes whose children it does not hold parks the run (`DAG_UNATTACHED_NODES_PAUSE_REASON`) and stops listening for commits.

## 2026-11-27 - DAG cancel stops every owned child; a superseded attempt is never adopted (#11381)

One child gate (`child-gate.ts`), with three rules each a single function, answers whether a child of a run may start, be revived, attached or folded:
1. no child of the run is live outside a current claim;
2. a settled run owes no stop;
3. the task in hand is its node's current attempt.

Admission, the re-entry sweep, recovery, explicit send, retry and amend, the self-resume fence and the read surfaces all call it.

The self-resume fence decides inside the record mutation from the run's checkpoint (same-process ordering; cross-process exclusion is the run lease's), and either retires the child or holds it. A refused turn counts as live until the runner confirms its stop (`TaskManager.selfResumeStopPending`; `task_self_resume_stop_confirmed` / `task_self_resume_stop_unconfirmed`).

Run cancel drains the run's live children to a fixed point and fails with `DagRunChildrenLiveError` while one stays live. A settled run owing a stop carries `outstandingStop` in snapshot, wait, attach and list (read once per batch) and refuses re-entry with `run_still_active`; amend validates before it drains. The record store keeps `owner.execAttempt`. Port of #11385.

Stacked on #15130 (#15125): every cancel road ends the run's children through that one drain, including the unheld cancel of a parked, user-stopped or crashed run and the cancel of a settled run (a failed run with a revived node: the child is stopped, the record keeps its status, the revive fold records the outcome and drops the lease). Send's revive, retry and re-entry, and the recovery of an interrupted run ask the child gate on the record their acquisition decided, after the ownership decision. A live child that is the current task of a node still running (a revive in flight) is not an owed stop. A cancel or send of a task with no refused turn keeps its synchronous start. The self-resume fence holds a current claim's turn while the user has stopped its run and records it on the node (`heldTrigger`, carried by a `node_flag` diagnostic so older builds replay it).

## 2026-11-27 - DAG nodes attach and fold during an admission batch (#10057)

The scheduler attaches each started child and folds settled ones while an admission batch is still in flight, instead of only between batches, so a long batch no longer starves folding. Port of #10054. Stacked on #15135, whose owner-wide cancel stops a child whose start returns after a batch error and a cancel.

## 2026-11-27 - A DAG node re-watches a child that resumes on its own (#12134)

The scheduler subscribes to a completed node's task through the optional `TaskManager.subscribeSelfResumed` and re-attaches it when the child reopens its turn, so the resumed outcome folds onto the node. The decision is the one `selfResumeVerdict` that #15135's self-resume fence also asks (the node's current claim of a run neither settled, being cancelled, nor stopped by the user): the scheduler re-opens a node only when that verdict allows and it holds the running run, so a turn started during cancellation is refused and never followed, a turn held while the user stopped the run re-opens nothing, and a turn allowed while the run is paused for a shutdown is followed by the scheduler that next holds it. A turn an explicit send starts is the send's, followed as revived, never as self-started. Stacked on #15134 and #15135, it has no cancellation drain of its own: #15135's run-wide stop covers a resumed child, asking a child again when it is live after an answer that found it stopped. Recovery re-opens, through the attach/fold gate every recovered node passes, a completed node whose task's latest run is self-resumed (`resumed_run_epoch === run_epoch`) and ended non-completed, or completed with an outcome other than what the node persisted (output and run_stats sidecar, both derived by the same `dagNodeResultContents` the fold writes with), and hands the task to the scheduler to fold; when a stale claim of the node cannot be stopped, the node fails closed (`stale_attempt_alive`) and the dependents that consumed its earlier output are flagged by the same `flagConsumedDependents` a folded resumed failure uses. No new persisted field. A persist without `run_stats` now removes an earlier fold's stats sidecar. A scheduler watches every completed node's task when it starts running (recovery, re-entry) and follows one already live under a self-resumed epoch. Each admission pass revalidates residency-denied nodes against their dependencies; one whose dependency is no longer completed returns to `pending` (reason `resumed`, the shape recovery uses for an unadmitted scheduled node), and a scheduled node without an attached task never counts as having consumed a dependency's output. A host that does not implement the subscription keeps the previous behaviour. Port of #11387.

## 2026-11-27 - Usage-limit turns settle in bounded time (#9711)

An announced provider retry is held for its stated delay and then settled, a terminal limit end is no longer dropped while a monitor is live, a spent provider is not called again for each child (also after a limit that ended a turn which had already run a tool), a task routed around a spent model waits for capacity on the model it actually runs, and an ambiguous limit's scope is probed once inside the turn that hit it, with that probe belonging only to its own run. Port of #11388.

## 2026-11-27 - A completed turn is held while the child's own async work is pending (#10487)

Every runner asks the child for its pending async work before settling a turn as completed and holds the turn while any is live; the held progress note is never the result: the turn the work wakes supersedes it, and work that drains with no new turn, or makes no progress within the bound, ends it as `async_work_pending`. A reopened or respawned session reads the same fact from the engine's `session-lifecycle` records in the session file, and a host park persists that outcome before it parks the record. A cancel ends an in-process child's held turn as `cancelled` in the same call (the handle's `markStopping`), so the session is destroyed at once and its work wakes no turn after the cancel; a wake turn already running ends `cancelled` and is never held again. Port of #12133.

## 2026-11-27 - Stranded children: refused warm revival, reused owner pid, paused orphans (#12077, #12080)

A refused warm revival restores the finished record instead of leaving it `running` with no outcome tracker; it keeps the current steering queue and burns the epoch the refused revival issued (as the cold rollback does), and neither it nor the cold rollback takes back a run whose stop was accepted (`cancel_requested`). Host claims carry a start-identity stamp so a reused pid is told from the live claimant; records written before this keep the signal-0 check. The workflow holder rule judges a node child's owner by the same function (`recordOwnerAlive`, start view injected through the holder probe's `ownerProcesses`), so a lease-less run is not left to a reused pid, and its lease watch waits for that stamped owner rather than the pid; a run's lease and previous holder stay bare pids. A child paused by its own run defers as `run_paused`, and both the scoped and the legacy reconcile sweep park a paused orphan for its run. The deferred scoped retry, the legacy owner retry and live-parent recovery recheck for a stopped session after observing the owner process, and the scoped pass those retries start sees the same stop before it admits anything. Port of #12078 and #12086.

## 2026-11-27 - A child whose revival is pending is neither orphaned nor held (#15150)

`TaskLifecycle.pendingRevivals` (`lifecycle/revival-pending.ts`) answers live-parent recovery's own revival obligation for a child (`obligation(taskId)`: `owed` while an attempt or expiry for it is in flight or it is still eligible - the final attempt past `recovery_deadline_at` included -, ownership first - `none` for a child this engine's current session does not own and once the lifecycle has no obligation, `stopped` once the lifecycle is disposed or the owned child's session stops its retries); `changed()` settles after every live-parent pass, at the end of every expiry, on dispose and when retries stop. `expiryInFlight` (`lifecycle/suspended-expiry.ts`) marks an expiry for its whole run. DAG recovery judges a non-terminal child with `childBacking` (`dag/child-backing.ts`): live, revival pending, or orphaned (#8657); never-launched children keep #12107 re-admission. A pending node keeps its state and goes to its scheduler as `awaitingRevival` (`dag/scheduler-pending-revival.ts`): it sits in the settle loop so its dependents wait and the run never parks, follows the child once it has a handle, folds a terminal record (a child the lifecycle gave up on folds there too when recovery finds it already ended, so the run's infrastructure retry applies either way), fails `resume_task_orphaned` once the lifecycle has no obligation, and is released without a journal write (the run parks) when the lifecycle stops; it keeps no clock of its own.

## 2026-11-27 - The DAG runtime takes a run only through the shared acquisition and reservation (#15125)

`ensureScheduled` (`dag-scheduler-registry.ts`) acquires a run only while it is still `pending` and builds the scheduler from the acquired record; a `running` run it does not hold goes to recovery. One reservation per run is shared by every entry and held for its whole operation: recovery from claim until adoption, retry, send, amend, guidance and node cancel (`dag-runtime-controls.ts`, refusing a reserved run with `run_busy`), cancel (`dag-run-cancel.ts`: it reserves first, waiting if needed, and only then decides whether there is anything to cancel), the user Stop (from retirement through its pause write, `dag-runtime-pause-wiring.ts`), the Resume's guidance dispatch, and the committed shutdown (every run it retires or pauses, `dag-runtime-shutdown.ts`). `pauseForShutdown` also closes recovery and lease watches first (`dag-recovery-sweeps.ts`). Only a running or installed scheduler means the runtime holds a run (`holdsRun`), and control verbs build no scheduler for a run it does not hold.

## 2026-11-27 - Workflow recovery asks the lifecycle about pending revivals (#15150)

The runtime's workflow recovery (`dag-runtime-recovery.ts`, split out of `dag-runtime.ts`) receives the engine lifecycle's `pendingRevivals`. The DAG widget row and the workflow tool's snapshot and detach text name a node whose unfinished child is suspended as waiting for its child to be revived (`dag-quiet-nodes.ts`).
