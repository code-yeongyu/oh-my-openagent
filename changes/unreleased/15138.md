### Fixed

- A background child no longer stays shown as running forever after a follow-up it refused: the finished run is restored when a warm revival prompt is refused, while a stop accepted meanwhile still ends it cancelled and messages queued meanwhile are kept. A reused process id is no longer mistaken for the child's live owner, a workflow run is no longer treated as held by another process when that process id was reused by an unrelated program, a child its own run paused reads as paused instead of held by another host, a paused orphan is parked for its run instead of being disposed or marked lost by any startup sweep, and a session that stops while a child's owner is being checked no longer has that child revived (#12077, #12080).

## 2026-11-27 - Stranded children: refused warm revival, reused owner pid, paused orphans (#12077, #12080)

A refused warm revival restores the finished record instead of leaving it `running` with no outcome tracker; it keeps the current steering queue and burns the epoch the refused revival issued (as the cold rollback does), and neither it nor the cold rollback takes back a run whose stop was accepted (`cancel_requested`). Host claims carry a start-identity stamp so a reused pid is told from the live claimant; records written before this keep the signal-0 check. The workflow holder rule judges a node child's owner by the same function (`recordOwnerAlive`, start view injected through the holder probe's `ownerProcesses`), so a lease-less run is not left to a reused pid, and its lease watch waits for that stamped owner rather than the pid; a run's lease and previous holder stay bare pids. A child paused by its own run defers as `run_paused`, and both the scoped and the legacy reconcile sweep park a paused orphan for its run. The deferred scoped retry, the legacy owner retry and live-parent recovery recheck for a stopped session after observing the owner process, and the scoped pass those retries start sees the same stop before it admits anything. Port of #12078 and #12086.
