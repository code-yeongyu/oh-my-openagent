# dag - Dependency-Frontier Task DAG Engine

Compile a node definition into an execution graph, admit each node the moment every node it dependsOn has completed (plus a free resident slot), journal every boundary transition to a filesystem WAL, and recover runs after crashes. Largest subsystem in senpi-task (35 files, ~13.9k LOC; added after the 2026-07 package snapshot). Public surface: `index.ts` barrel + package subpath `./dag`; consumer is the omo-senpi task component (`dag-runtime.ts`, `dag-tool.ts`, `dag-rpc-bridge.ts`).

A send is decided ONCE, on one fresh record under one run lock (`decideSend` through `acquireDagRun` with `classifySend` and `leaseWhen`), into a closed set: `guidance` (user-stopped), `steer` (live run, no lease), `revive` (failed run, this host's lease written in that lock), or a typed refusal; only steer and revive reach the child, and the steer record is decided again at its write (`steerRecordRefused`). This host holds a revived run from the first revive acquisition until the fold of the LAST revive, counting revive-sends still in flight: the revive watcher's fold waits for the run's reservation, so it is written after any in-flight send of this host, and only while the node still runs that child; a send that wrote the lease and then did not revive gives exactly that lease back (`leaseTaken`). Once the task manager answered `revived` the send never gives the lease back: the watcher is armed before any fallible write and owns the lease's end (it folds, or, if the node never became running, releases the lease when no node is active). `DagSchedulerOptions.reservations` is required, so no watcher can fold without the run's reservation. Codes `node_not_found` / `node_not_retryable` / `node_not_continuable`. |
| `recovery.ts` | `createDagRecovery`: durable-owner reconciliation, journal replay, result reuse, scheduler re-entry, lost-task handling. `installPausedRuns` claims and installs like `resumePausedRuns` but resolves once each claimed run's scheduler is installed (`dag.run.resumed` journaled), handing every `InstalledDagRun` to the caller's `adopt`; `resumePausedRuns` still awaits each run's `settled`. Reconciliation NEVER awaits a still-running reattached child; it hands the child to the scheduler through `preAttachedTasks`. A `live_lease` skip reports the `holderPid` it saw alive so the caller can retry once that host is gone. A holder pid equal to the host's own pid is judged by the injected `isRunHeldInProcess(runId)` (default: not held), never by signal-0, so a same-process session reopen claims the run while a same-runtime pause + re-attach still skips it. A run left `running` (its host died before the shutdown pause could be written) is claimed the same way, but only when `isRunHeldInProcess` is injected and answers that no scheduler here holds it, and its holder is gone. Claims (`recovery-claim.ts`) and the shutdown pause (`recovery-shutdown.ts`) go through the one acquisition; a claimed run's reservation ends only when the caller adopts its `InstalledDagRun` (`release`), so no other entry of the process can touch the run in between. `pauseRunsForShutdown` pauses only runs this host holds or whose holder is gone. |
| `run-acquisition.ts` | The one way this host takes a run (#15125). `acquireDagRun` runs under the run lock on the FRESH checkpoint: the caller's eligibility (statuses and parent session), the holder rule, this process's per-run reservation (`createDagRunReservations`: one operation per run at a time; `whenFree` / `whenAllFree` for the waiters), then the lease, and returns the exact record acquired (or not eligible / held by pid / busy / missing). Every entry that schedules or mutates a run uses it and passes exactly one named predicate from `dagRunEligibility` (the entry's full rule, in that one file): `freshStart`, `reentry` (NO active node, terminal or paused alike: a node revived by a send refuses a retry or amend `run_still_active` naming it until its fold; refusals in `reentry-refusal.ts`), `parkFailed`, `automaticRecovery` (never a run the user stopped), `forkSourceAdoption`, `userResume(pauseSeq)` (exactly the Stop being resumed), `unheldCancel`, `shutdownPause`, `userStop`, `send` (with `classifySend`), `stoppedWrite(pauseSeq)`. The reservation registry lives in `run-reservations.ts` (re-exported here); `leaseWhen` lets one acquisition decide lease-or-no-lease from the fresh record, and `leaseTaken` tells the caller whether it wrote the lease. The entry decides and writes from the record returned (`acquireReentryLease` hands it back with the release; retry validates its targets on it); an earlier read is only ever a fast refusal. A reservation the acquisition created is released if its own lease write throws; a caller-owned one (`reservation`, or `DagRunHeldReservations` handed to `pauseRunsForShutdown`) never is. A reserved run refuses model-driven verbs with the retryable `run_busy`. `decideDagRun` is the same lock-held decision without taking anything; the user Stop evaluates it inside its journal's locked `skipDuplicate` (`controlJournal`'s `skip`), so the read that decides is the read the pause is appended to. Every write to a user-stopped run (guide add/edit/remove, node-cancel request and transition, retry staging, the Resume's guidance delivery records) goes through `appendWhileStopped` (`paused-controls.ts`), decided at the write under the journal lock by both facts: the same Stop (`stoppedWrite`) and no other live holder (`run_not_owned` with the holder pid, else `run_not_user_paused`). An amendment of any paused run, a user-stopped one included, is refused while another live process holds it by the one holder rule (`DagAmendParams.holder`, decided in the amend journal's lock). |
| `run-lease.ts` | Who holds a run. The lease leaves the record only in the write that ends this host's holding (`leaseAfterEvent`, applied by the scheduler and recovery reducers): a terminal status, a park or a user Stop drops it, the shutdown pause hands it over as `previousLeaseHolderPid`, and on a settled run the fold of the last revived node out of `running` drops it; a scheduler merely retired keeps it. `runHolder` is the one answer to who holds a record (lease, then previous holder, then for a record naming neither `liveChildOwner`: the live foreign owner of a node's current, unfinished child via `currentNodeTask`); `liveForeignHolder` over it is asked by every acquisition and by `ownedRecord` (every control verb). The amend write asks it too: `DagAmendParams.holder` is the caller's `liveForeignHolder` with its probe (`foreignHolderOf`), evaluated in the pre-check and in the amend journal's lock-held `skipDuplicate`; a held paused run is never amended (`run_not_owned`), and the mutation reducer carries no liveness probe, so replay is deterministic. |
| `recovery-lease-watch.ts` | `createDagLeaseWatch`: polls a paused run's still-alive previous holder pid (signal-0, unref'd timers, injectable) and fires once when it exits; the adapter re-runs recovery on that signal. |

## Admission semantics

- A node starts once EVERY node it dependsOn holds `completed` and a resident slot is free (dependency-frontier admission). Compiled waves NEVER gate execution; `dag.wave.started` groups the nodes one admission pass scheduled (one wave index can appear in several started events when its nodes become ready at different times) and `dag.wave.completed` fires once per index when the wave's FULL membership is terminal (skipped and failed nodes included in the listing).
- The dependent skip cascade runs at frontier quiescence (nothing attached): a failed node stays revivable via `send` while siblings are mid-flight, so an eager cascade would strand revived-completable dependents as skipped. A pass whose every admission failed at start (nothing attached, dependents still pending) re-enters the loop so the cascade settles the run instead of throwing (#8396).
- The resident-child cap is SESSION-wide (`lifecycle/residency.ts` counts every resident record of the parent session), so a residency denial parks the node (`scheduled`, journaled once as `residency_queued` with `residents` / `heldByOtherOwners`) and the scheduler waits on `Promise.race([own settlements, taskManager.residencyChanged(parentSessionId), foreign journal commit, cancellation])` - never on its own `attachedTasks` alone, which is empty for a run that arrives second (#8396). Only a denial naming NO resident (`cause: "residents"`, empty list) terminal-fails the node; a `cause: "lease"` denial re-probes at once because lease acquisition is itself a bounded wait. An admission batch is open-ended (a start can take minutes against a busy task host): each start is handled the moment it returns, the run's own children fold the moment they settle, and the nodes a fold unblocks join the batch at once; denials stay in admission order (#10057). The batch's first processing error (a journal, attachment or fold fault) stops it from handling or launching anything more, but it keeps the admission latch until every start still in flight has returned (unhandled, as if the batch had ended on that error after they settled), then rejects the run with that error whichever event the batch was waiting on.

## Recovery launch boundary

Recovery resolves the newest owned task of the node's CURRENT `execAttempt` (`recovery-attempt.ts`, classified by `owned-attempt.ts`, the rule the re-entry sweep and admission share) before consulting the checkpoint's `taskId`: `dag.node.retried` retains the prior ID until the replacement's admission batch attaches it. That prior record must not override the replacement's launch evidence or terminal outcome, and a task of an earlier attempt is never folded or re-attached: a live one is stopped before the node starts afresh, and the node fails closed with `stale_attempt_alive` when it cannot be stopped (#11381). A recovery retry event names the selected task in `priorTaskId`, not the checkpoint's retained ID.

`TaskRecord.started_at` is durable before normal start or lifecycle respawn invokes a runner. Respawn preserves an existing stamp without changing status or epoch; non-terminal reattachment stamps any absent value when writing `running`. A DAG node may remain `scheduled` after its child starts, so only a scheduled, lost task without this stamp is eligible for automatic readmission. Recovery uses `dag.node.retried` with `execAttempt + 1`, capped at three. Stamped lost work folds `task_lost`; legacy unstamped scheduled records remain eligible. A crash after stamping but before invocation conservatively folds `task_lost`. Reconciliation loss reduces the current stored record under its record lock, including when respawn fails after invoking the runner; it must preserve the launch stamp and other facts persisted during respawn.

## Owned children: one cancellation rule (#11381)

- **One child gate** (`child-gate.ts`): may a child of this run start, be revived, be attached or be folded now? It is three rules, one function each, and every point calls them:
  1. no child of the run is live outside a current claim: a superseded attempt's, a removed node's, or a refused turn whose stop is not confirmed (`staleLiveChildren`, with liveness from `isLiveOwnedTask`);
  2. a settled run owes no stop (`outstandingStopRefusal`);
  3. the task in hand is its node's current attempt (`ownedClaimAge`).

  The points are admission, the re-entry sweep, recovery start/attach/fold (the interrupted-run claim of #15125 included), explicit send, retry and amend, the self-resume fence, and the read surfaces. They differ only in what they do with a refusal. An entry that takes or mutates a run decides ownership first (acquisition, holder, lease, under the run lock) and asks the gate on the record it decided from, never an earlier read: send's revive branch after `decideSend` (a refusal gives back exactly the lease the send took), retry and re-entry on the acquired record (`assertNoOutstandingStop` in `run-reentry.ts`; the acquisition's lease is abandoned).
- **Two liveness questions, two functions.** "Which PROCESS holds this run" is the holder rule (`runHolder` / `liveForeignHolder`, `run-lease.ts`): lease, previous holder, live foreign owner of a node's current child. "Which TASKS of this run are live" is `isLiveOwnedTask` (`scheduler-context.ts`): an unsettled record, or a refused turn whose stop is not confirmed. Acquisitions ask the first; the gate, the drain and the outstanding stop ask the second. Neither stands in for the other.
- **Resume fence.** A settled child runs again only through the manager's self-resume reopen. The manager asks `owner-resume-fence.ts` inside the record mutation, and the answer rests on the run's checkpoint, which every journal append rewrites synchronously. That gives same-process ordering for the process holding the run; exclusion across processes is the run lease's job.
  - `retire` covers a superseded or removed claim and a cancelled or cancelling run, and ends the child.
  - An explicit send (`TaskManager.sendToTask`, so `task_send` too) asks the same fence first, on the record the address resolves to (steering's one resolver): `retire` is refused `not_continuable` with the owner's remedy and the child is never touched (a live superseded child is not steered either: its claim is over and the run's fence stops it); `hold` keeps the explicit send/revive contract; a record no owner fences is untouched.
  - `hold` covers a current claim of a failed or completed run, and of a run the USER stopped (paused with `pause.reason` `user_stop`). It stops only the unsolicited turn and keeps the child resident and send-revivable. A run paused for a shutdown keeps allowing: the next holder follows the turn.
  - A hold on a user-stopped run is recorded on its node (`heldTrigger`: task id, cause, count, first and last time; `held-trigger.ts`), written after the refusing mutation through `appendWhileStopped` (same Stop, no other live holder, decided at the write; a refused write writes nothing and the turn stays held). It rides the existing `dag.diagnostic.added` event as a `node_flag` diagnostic, folded into the node by this build's reducer (`held-trigger-record.ts`) and merely listed by an older one, because an older build's replay throws on an unknown event type. It is shown in the tool's snapshot and attach text and on the widget's node row, and cleared when the node is next sent to, retried, amended or moved to `running`. Resume does not revive the child.
  - The decision is one function, `selfResumeVerdict`. The scheduler holding the run asks the same verdict before a node re-opens to follow an allowed turn (`scheduler-self-resume.ts`, told through `TaskManager.subscribeSelfResumed` only when the fence allowed it), so no allowed turn goes unfollowed and no refused turn re-opens a node. A turn allowed while no scheduler holds the run (a shutdown pause) is followed by the scheduler that next holds it; recovery re-opens a completed node for an ended self-resumed run only through `resolveRecoveredNodeTask`. A turn an explicit send starts is the send's, never announced as self-started: the send's revive watcher follows it.
- **Refused turn, stop not confirmed.** The manager marks this (`manager/refused-stops.ts`) in the same step as the refusal, and clears it only when the runner confirms: for a hold, the abort settled and the turn's outcome was observed; for a retire, the teardown settled; or the handle is gone.
  - Until then the task counts as live everywhere (`TaskManager.selfResumeStopPending`). A timed-out or rejected step keeps it (`task_self_resume_stop_unconfirmed`).
  - A cancel awaits or re-issues the stop; a hold becomes a retire once the run is cancelled or cancelling.
  - A send awaits the stop and answers the retryable `unresponsive` while it is unconfirmed.
  - The marker is in memory. An in-process child's turn dies with its process; a host-session child's turn that outlives the process is not re-fenced by a new process (see the #15135 report).
- **Stopping and admitting.**
  - Run cancel drains the run's whole live set to a fixed point and fails with `DagRunChildrenLiveError` while a child stays live. The run's children are every task whose owner record names the run plus an owner-less child a node of the run names (`liveRunChildren`, the one definition the drain, the gate and the outstanding stop share). That drain (`stopRunChildren`, inside the scheduler's cancel) is the one cancellation rule on every road: a held scheduler's cancel, the unheld cancel of a parked, user-stopped or crashed run, the park after a repeated scheduler failure (`dag-scheduler-failure.ts`: a node whose child did not stop stays active instead of being failed), and the cancel of a settled run (a failed run with a revived node included: its child is stopped, the record keeps its status, and the revive fold records the outcome and drops the lease). A cancel never awaits a revive fold, which waits for the cancel's reservation. A child is asked again only when it is live after an answer that found it stopped (it started a turn on its own meanwhile); an answer that found it still running is reported, not repeated. Only the first stop of an attached child on the run it was attached on defers its in-process teardown (`abort: "skip"`, bound by `expectedRunEpoch`); a self-resumed run is cancelled outright.
  - Admission and recovery never start a node while a rule-1 child survives its stop; the ready nodes fail with the retryable `stale_attempt_alive`.
  - The owned start refuses start and reuse while another live claim exists.
  - Recovery stops stale claims before it returns a current one, and reads the current claim again after any awaited stop.
- **Outstanding stop.** It is derived, not stored: a terminal run that still owns a live child owes a stop, except the current child of a node still `scheduled` or `running` (a revive in flight, #15125: the run holds it). The drain still stops that child.
  - Snapshot, wait, attach and list carry `outstandingStop`; the list reads the task records once per batch.
  - The dag tool and the status widget name it.
  - Send, retry and re-entry refuse with `run_still_active`. Amend validates first, then drains, and refuses if a child stays live.

## Conventions

- Policy is fixed inside the definition fingerprint: `dependency-frontier` wave admission (was `strict-barrier` before 2026-08-25), `continue-independent` failure handling, filesystem-only dependency data.
- Run reuse keys on the SUBMITTED definition (canonicalized). Amendments preserve eligible node state and invalidate affected dependents.
- Boundary events are sequenced by the journal writer; live telemetry rides the unsequenced `omo.dag.activity` channel as a separate union.
- Node target rules mirror the task tool: category XOR `subagent_type`, model only with a custom agent route, error codes `both_targets` / `no_target` / `category_with_model` / `agent_with_model`.

## Anti-patterns

- NEVER fold skill content, skill digests, or effective prompts into definition fingerprints; reuse must survive skill materialization changes.
- NEVER key recovery by display attempt; read the persisted `execAttempt` (reattach bumps the display attempt).
- NEVER resume a prior scheduler instance; cancellation deferreds and admission latches are single-shot. Use re-entry / retry / send controls. A re-entry drops `preAttachedTasks`: those ids describe children that were live for the PREVIOUS instance, and re-attaching a settled task folds its outcome onto the node twice.
- NEVER treat a `live_lease` skip as final for an own-session run. The predecessor host that paused the run for its shutdown is usually still draining when the successor resumes the session (omo-desktop RPC restart), so a one-shot claim at `session_start` leaves the run paused forever; watch the reported `holderPid` and claim again when it is gone.
- NEVER leave a run `running` with no scheduler. A host killed mid-run writes no pause, so recovery claims its `running` run like a paused one (#15125); a scheduler that finds active nodes whose children it does not hold parks the run as paused (`DAG_UNATTACHED_NODES_PAUSE_REASON`) instead of throwing, and nothing may build a fresh scheduler over a `running` run it does not hold: the lease decides, and recovery alone claims. A parked run's verbs follow from that: cancel stops every child the run owns (the one drain) before journaling the run cancelled, and retry or amend refuse with `run_still_active` (`refuseUnheldActiveNodes`) while a non-user pause still records active nodes. A frontier that returns the run paused stops listening for commits.
- NEVER probe our own pid for lease liveness. A signal-0 check on `process.pid` is always true, so a saved session reopened in the same multi-session host (fresh runtime, same `parentSessionId`, same pid) would wait for its own host to exit (#8006). For `holderPid === hostPid` the only holder that can matter is a scheduler still registered in this process; ask `isRunHeldInProcess`, and never arm a lease watch on our own pid.
- NEVER block recovery's reconcile loop on a live child. A restart must emit reuse events and `dag.run.resumed` immediately and let the still-running child fold through the normal settle loop, or the run sits in `paused` for as long as the slowest child runs and every operator lever (amend, retry) refuses on `run_still_active`.
- NEVER put activity events or journal seq/lane metadata into boundary builders.
- Missing skills never fail a run; they become `missing_skill` diagnostics. Resumed runs read creation-time materialization, never current `SKILL.md`.
- Wait surfaces resolve (not reject) failed/cancelled runs; callers inspect `DagRunResult`.
- A vanished `<stateDir>/dag/*` directory (worktree cleanup, `rm -rf .omo`) reads as empty through `readDagDirectory` and is recreated by the next checkpoint/event/lock write; it must never surface as an ENOENT from `list`, retention, or recovery. The omo-senpi rpc bridge additionally treats any store read fault on its timer paths as "nothing to publish" (one warning per distinct fault), because a throw there is an `uncaughtException` that ends the session.
