## Ordering decision: option (2), with the ordering pinned by a regression test

Finding 1 offered two escapes. I measured both before choosing.

Option (1) as written ("snapshot on `turn_end`/`agent_settled` instead of `session_shutdown`") solves
the *snapshot* half of the hazard but cannot solve the *emit* half, and the emit is the half that is
actually destroyed. Measured:

```
$ bun run /tmp/t6scratch/probe2.ts
post-shutdown turn_end captured anything new? 0 []
```

After `session_shutdown`, `state.capture` is `undefined` and every capture is a silent no-op. So the
emission itself must run while capture is still live. Neither `turn_end` nor `agent_settled` knows it
is the last one of the session, which leaves only two ways to emit there, and both are forbidden by
this todo:

- emit on every `turn_end` -> per-turn emission, the exact volume blowup the once-per-session bound
  exists to prevent;
- emit on the first `turn_end` only -> silently drops every later turn's waves.

So the emit must happen on `session_shutdown`, before the session component tears the client down.
That is option (2). Its stated weakness is that it is "invisibly order-fragile", so I removed the
invisibility in two ways:

1. `registerOmoNativeParallelSummary` owns the ordering internally. It registers its own
   `session_shutdown` handler and only *then* calls `registerOmoNativeParallelTelemetry`, so the
   registry-clearing handler can never precede the snapshot-reading handler. The caller cannot get
   that half wrong.
2. The remaining caller-side constraint (call it before `createOmoNativeSessionComponent`) is pinned
   by a regression test that drives the REAL component and is proven below to fail under mutation.

Measured registration order through the real component (`/tmp/t6scratch/qa.ts`):

```
registration order: session_shutdown -> tool_execution_start -> tool_execution_end -> turn_start ->
turn_end -> session_shutdown -> input -> input_disposition -> session_shutdown -> session_start ->
session_shutdown -> turn_end -> tool_result -> session_shutdown -> session_start
```

The emitting `session_shutdown` is first; the session component's teardown `session_shutdown` is
fourth. The registry still ends at size 0 because the emitting handler calls `registry.clear()`
itself immediately after consuming the snapshot.

### Reading the QA numbers

The session drove four waves: W1 = three overlapping non-eval calls (bash/read/grep), W2 = one
eval-only call, W3 = a mixed wave (eval + bash overlapping), W4 = two overlapping non-eval calls
(write/edit), plus a fifth start with no end.

- `non_eval_waves_total: 2` counts only W1 and W4. W2 and W3 are excluded, as required.
- `non_eval_joined_calls: 5` = 3 (W1) + 2 (W4). The mixed wave's `bash` call is NOT folded in;
  folding it would have produced 6 and inflated savings, which Finding "never fold mixed" forbids.
- `eval_only_waves: 1` / `eval_only_duration_ms: 26` / `mixed_waves: 1` carry their own buckets.
- `incomplete_calls: 1` is the dangling `webfetch` start.
- `non_eval_wave_size_histogram: "0:1:1:0:0:0:0:0"` = positional buckets `1,2,3,4,5_8,9_16,17_32,33plus`:
  zero waves of size 1, one wave of size 2 (W4), one of size 3 (W1). 15 chars, no labels, no `=`,
  well under the 64-char truncation that destroyed the labelled form.
- `upper_bound_saved_ms == modeled_wallclock_saved_ms` here is a coincidence of this fixture, not a
  bug: the calls started near-simultaneously with near-equal durations, which is exactly the case
  where `savings-math.ts` documents the two formulas converging. The unit tests assert a fixture
  where they diverge.
- `turn_completed` count is 0 in this driver only because no `turn_end` with a usage payload was
  dispatched; the component integration test separately asserts the `turn_completed` stream is
  unchanged.

## Adversarial classes probed

| Class | Probe | Result |
| --- | --- | --- |
| Misleading success output | MANDATORY MUTATION: emit moved after transport cleanup | Regression test FAILS with `Received length: 0` while the unit suite stays 13/0 green. The test provably pins the criterion. |
| Stale state - two sessions mixing | Two sessions interleaved, each shut down | Each emits its own payload with its own `$session_id` and its own `non_eval_joined_calls` (1 vs 2). No cross-contamination. |
| Stale state - double emission | Same session shut down twice | Exactly 1 event. Snapshot is consumed and the session cleared in the same handler, so the second shutdown finds nothing. |
| Stale state - second shutdown emits nothing | Covered by the above | 1 event total, asserted. |
| Malformed input - only anomalous/incomplete calls | Session with one never-ending start plus one reversed-clock pair | ZERO events. Quality counters alone do not justify an emission, so no corrupt all-zero payload reaches the wire. |
| Malformed input - idle session | Shutdown with no activity at all | ZERO events. |
| Malformed input - turn with no tool calls | turn_start/turn_end, no tool events | ZERO events (a non-zero `measured_turn_duration_ms_total` alone is not reportable parallelism). |
| Repeated interruption - shutdown mid-turn | Two completed calls + one in-flight start, then shutdown, then the late end, then a second shutdown | Exactly 1 event, `non_eval_joined_calls: 2`, `incomplete_calls: 1`. The late end does not resurrect the session or produce a second event. |
| Unattributable shutdown | `session_shutdown` with no resolvable session id | ZERO events and the live session survives to emit its own payload afterwards. |
| Cap saturation under-report | 2500 starts against `MAX_TRACKED_CALLS = 2000` | `dropped_calls: 500` on the wire; four-sink invariant closes at 2500. |
| Privacy leak | 80-char needles in `args`/`result` | Needle absent from the payload. |
| Allowlist conformance | Emitted keys vs `OMO_NATIVE_PROPERTY_ALLOWLISTS.parallelism_summary` | Exact match (plus the 5 shared keys the privacy wrapper adds). |

### Ruled out with reason (not probed further)

- **Per-wave / per-turn emission** - structurally impossible: the only `captureEvent` call site sits
  inside the `session_shutdown` handler, and no other handler in the module captures anything.
- **`turn_completed` regression** - the diff contains no `turn_completed` schema or handler change;
  its single occurrence is a read-only test assertion. Verified by `git diff | grep turn_completed`.
- **`max(d)` savings basis** - `grep "Math.max"` on the new module returns NONE; all savings come from
  `savings-math.ts`, which is span-based and was not modified.
- **Unbounded observation buffer (Finding 4)** - out of scope and deliberately not made worse: the
  adapter projects `calls -> toolNames` per wave transiently and retains no second copy of the
  observations.
- **Forbidden packages** - `git status` shows no change under `packages/telemetry-core/`,
  `packages/omo-codex/`, `packages/omo-opencode/`, or `packages/omo-senpi/plugin/extensions/`.
