## Script audit (performed before trusting PASS)

### Vacuous-pass analysis

The script does **not** pass vacuously on an empty capture:

- `parseCapturedEvents()` can return an empty array, but `assertEnabled()` immediately requires exactly three captured native `prompt_submitted` events with `is_real_user_prompt === true`.
- It then requires every one of the seven native event names to exist: `daily_active`, `session_started`, `prompt_submitted`, `turn_completed`, `skill_loaded`, `delegation_started`, and `feature_used`.
- It additionally requires positive token data, the goal-tool feature event, and the legacy `omo_senpi_daily_active` event.
- Although `privacyScan()` alone would have no loop iterations for an empty array, it is only reached after the non-empty enabled assertions above. Therefore the full script cannot report PASS from an empty native capture.

### Real CLI versus fallback

There is no fallback that silently replaces the CLI drive:

- `main()` resolves a Senpi executable and throws if none exists.
- `runHelp()` spawns that executable and rejects a non-zero result or a CLI lacking the required non-interactive capability.
- Every enabled/opt-out drive calls `driveCli()`, which directly `spawn()`s the resolved Senpi executable in `--mode rpc`.
- A deterministic temporary provider supplies model responses and tool calls, but it is loaded into the real Senpi CLI together with the real built OmO plugin. It is not an alternate telemetry emitter or a substitute CLI drive.
- A failed child, timeout, non-zero child exit, or fewer than three `agent_end` events rejects the drive.

### Hardcoded-value and exception audit

- Expected classifications and event names are constants, but assertions compare them against parsed captured event properties; they are not unconditional PASS values.
- Request counts are calculated from capture-file lengths before and after each drive.
- Malformed captured request JSON is skipped, but missing events then fail the required enabled assertions rather than becoming PASS.
- Narrow `catch {}` blocks only ignore non-JSON CLI transcript lines or parsing attempts; they do not convert drive/assertion failures into passes.
- The top-level `main().catch(...)` exits 1 for failures and 2 for a blocked CLI claim. No failure-to-pass catch exists.

Audit conclusion: **non-vacuous**.
