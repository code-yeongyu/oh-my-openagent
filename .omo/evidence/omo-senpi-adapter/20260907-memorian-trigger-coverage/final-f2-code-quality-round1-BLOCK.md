### B2 — Tool singles do not prefer path-derived words, so the filename the feature exists to surface is often crowded out

- Evidence:

## Notes (non-blocking)

**N1 — `outcome.json` is not written on the setup-race and setup-failure paths.** `memorian-judge-run.ts:40-54` `record()` runs for every terminal return, but `writeMemorianRunOutcome` writes into `runDir`, which is created inside `setup` at `:64`. If the deadline fires before that `mkdir` resolves, or if `mkdir`/`writeFile` is what failed (the `session_create_failed` catch at `:126-128`), the write ENOENTs and only warns. Probe: `writeMemorianRunOutcome({ runDir: "<missing>/run-x", status: "dropped", cause: "deadline", ... })` → `outcome.json exists: false`, `warns: [["memorian run outcome write failed", {..., "error": "ENOENT: ... open '.../run-x/outcome.json'"}]]`. Consequence: the tail-latency evidence the 30-day deadline class exists to preserve (plan todo 7(D)) is missing for exactly the fastest-failing deadlines. A `mkdir(runDir, { recursive: true, mode: 0o700 })` inside `writeMemorianRunOutcome`, or hoisting the `mkdir` out of `setup`, closes it.

**N2 — separately: the persisted outcome can contradict the launch result.** `memorian-runner.ts:178` (`dropped/cancelled`) and `:189-191` (`dropped/compaction`) are terminal for the *launch* but run after the judge already recorded `completed`. A compaction-dropped run therefore keeps `{"status":"completed","nudged":["..."]}` on disk and is retained 30 days as a "nudged" run even though nothing was ever delivered. Within the plan's letter (it only required writes "in `memorian-judge-run.ts`"), but it makes `outcome.json` an unreliable audit record and over-retains transcript excerpts, which is the opposite of the retention module's stated privacy rationale.

**N3 — an empty run dir is never pruned at any age.** `memorian-run-retention.ts:105` treats `newestFileMtime(dir) === undefined` as keep, and `newestFileMtime` (`:152-157`) returns `undefined` for a directory with no entries. Probe: a 400-day-old empty `runs/empty-old` next to an 8-day-old `runs/old-file` → `result {"removed":1,"kept":1}`, `empty-old still exists: true`, `old-file still exists: false`. A judge that dies between `mkdir(runDir)` (`memorian-judge-run.ts:64`) and the first `writeFile` (`:68`) leaks one such dir permanently. Falling back to the dir's own `stat().mtimeMs` when it has no entries fixes it without weakening the running-judge guard.

**N4 — `wiring-memorian.ts:75-89` re-lists the `MemorianTrigger` members by hand.** Correct and type-checked today (`MemorianTrigger` is closed at `memorian-trigger.ts:49-55`, `tsgo` exit 0), but a member added later silently needs this literal updated. `{ ...trigger, onSettled(eventCtx) { ... } }` is equivalent and cannot drift.

**N5 — `s6.tool-fixture` cannot fail for what it names.** `memorian-tool-boundary-e2e-scenarios.mjs:204` asserts only properties of the module constant declared at `:21-34`. It is a fixture invariant, not a scenario assertion; the real proof is `s6.arg-harvested` at `:242`.
