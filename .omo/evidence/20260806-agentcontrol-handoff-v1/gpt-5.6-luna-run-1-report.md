## Flow

- **Public launch surface and forwarding.** `packages/omo-opencode/src/tools/agentcontrol/tools.ts:52-83` defines the four direct launch tools (`Execute`, `Explore`, `Plan`, `Research`) from one factory. Their shared schema requires `handoff: tool.schema.string().min(1)` at lines 57-68, and `execute()` forwards the complete input through `call(action, input, context)` at lines 73-81. `Dispatch` separately requires the same non-empty handoff path at `tools.ts:110-127` and forwards it through `call("Dispatch", input, context)` at lines 120-121. The focused adapter test confirms every launch action has a required `handoff` argument and that all five paths preserve the supplied path (`packages/omo-opencode/src/tools/agentcontrol/agentcontrol.test.ts:52-63,139-167`).
- **Python public schema.** The four direct MCP schemas are generated by `_agent_action_tool()` in `tools/agent_control/mcp_server.py:300-337`; `handoff` is a required string with `minLength: 1` at lines 306-307 and 331-335. The Dispatch schema requires `template`, `items`, `group`, and `handoff` at `mcp_server.py:343-370`, with the handoff description at lines 361-363.
- **Validation-to-launch path.** `MCPServer.call_tool()` validates direct actions before calling `spawn()` (`mcp_server.py:548-558`) and validates Dispatch before calling `dispatch()` (`mcp_server.py:559-564`). `_validate_handoff()` rejects a missing/non-string path with `HANDOFF_REQUIRED`, calls the contract validator, and converts validation failures to structured `REJECTED` responses (`mcp_server.py:582-590`). The focused regression test proves a missing handoff returns `HANDOFF_REQUIRED` and leaves the ledger with no workers (`tests/agent_control/test_mcp_v3.py:2143-2151`). Dispatch does not create its workflow or pending rows until after this validation returns metadata: `dispatch()` begins at `mcp_server.py:816-824`, then creates the workflow at lines 834-840 and pending rows at lines 844-868. Therefore rejection precedes both worker creation and Dispatch pending-row creation.
- **Worker launch and metadata propagation.** Direct workers persist metadata in the ledger insertion at `mcp_server.py:697-704`, then receive the same trusted values in `AGENT_CONTROL_HANDOFF_ID`, `AGENT_CONTROL_HANDOFF_PATH`, and `AGENT_CONTROL_HANDOFF_SHA256` at lines 722-737. Dispatch persists the values per item at `mcp_server.py:847-855`; when pending items become runnable, `_launch_run_worker()` copies those persisted columns into the worker environment at lines 926-951. The ledger schema stores all three columns at `tools/agent_control/ledger.py:29-60`, migration support adds them for older databases at lines 82-98, and `add_worker()` inserts them at lines 124-169. The direct and grouped propagation tests assert the exact ID, absolute path, digest, and per-item persistence (`tests/agent_control/test_mcp_v3.py:2184-2203,2206-2229`).
- **Worker prompt contract.** `packages/omo-opencode/src/plugin-handlers/agent-config-finalizer.ts:16-44` reads the selected preset plus worker name/report path and the three handoff environment values, serializes them into runtime JSON, and appends the contract to the selected agent prompt at lines 47-61. The contract explicitly says to read the handoff before any other task work, treat claims/decisions as inputs to revalidate rather than conclusions, inspect authoritative sources independently, follow scope/acceptance/mutation/verification boundaries, call `Report` once with a blocker if it cannot be read, and call `Report` exactly once per leader request (`agent-config-finalizer.ts:41-44`). The focused test verifies the runtime JSON fields and the read-first/revalidation/blocker instructions (`agent-config-finalizer.test.ts:102-143`). The worker-only adapter surface exposes only `Report` (`tools.ts:91-101`), matching the role split.

## Rejection

- `validate_handoff()` resolves the launch project and supplied path, makes relative paths project-relative, requires an existing regular file, and rejects paths outside the project (`tools/agent_control/handoff.py:93-107`).
- It enforces the 128 KiB limit and UTF-8 decoding (`handoff.py:109-118`), then requires frontmatter with no duplicate keys and all six metadata fields (`handoff.py:13-15,48-70`).
- It requires schema `agentcontrol-handoff/v1`, an ID matching `^[a-z][a-z0-9_-]{0,63}$`, exact action match, `status: ready`, and a resolved `projectRoot` equal to the launch project (`handoff.py:119-135`).
- Required sections are `Goal`, `Done when`, `Workspace`, `Scope`, `Source map`, `Claims and decisions`, `Acceptance atoms`, `Verification`, and `Deliverable`; `Execute` and `Dispatch` additionally require `Mutation boundary`. Duplicate, missing, and empty required sections reject (`handoff.py:14-25,73-90`).
- The validator returns canonical absolute `path`, ID, action, source revision, and SHA-256 over the exact raw bytes (`handoff.py:36-46,137-143`). The focused rejection matrix covers empty section, action mismatch, outside-project path, and oversized content (`tests/agent_control/test_mcp_v3.py:2154-2181`).

## Dashboard

- `monitor.snapshot()` reads ledger rows for one owner/group and carries `handoff_id`, canonical path, launch-time SHA-256, status, and verified content into each item (`tools/agent_control/monitor.py:86-103,130-147`).
- The per-refresh shared read cache is the local `handoff_cache` dictionary at `monitor.py:103-104`, keyed by `(handoff_path, handoff_sha256)` at lines 130-133. Thus Dispatch workers sharing one path and digest perform one `_load_handoff()` per snapshot refresh, while differing launch metadata remains separately checked.
- `_load_handoff()` requires a project-local regular file, enforces the same maximum size, decodes UTF-8, hashes the current bytes, and returns `verified` only when the current digest equals the persisted launch digest (`monitor.py:63-83`). A mismatch returns `("changed", "")`, not current content, which prevents substituted handoff text from being displayed.
- The wide dashboard inspector shows `handoff <id> · VERIFIED` or the other status (`monitor.py:409-425`). The footer advertises `H handoff` (`monitor.py:459-469`); key handling switches the selected item to the handoff view at `monitor.py:803-810`, and the render loop calls `render_handoff()` for that view at lines 713-716. `render_handoff()` displays the ID, status, SHA-256, canonical path, and only the verified content (`monitor.py:511-545`). The focused test verifies metadata, `VERIFIED`, H affordance, full document content, then mutates the file and proves status becomes `changed`, content is blank, and substituted text is absent (`tests/agent_control/test_mcp_v3.py:2232-2260`).

## Risks

- `sourceRevision` is required as non-empty frontmatter metadata (`handoff.py:15,67-70`) and is persisted in the returned metadata object (`handoff.py:36-43`), but this implementation does not compare it to the current Git revision; revision freshness remains a worker/leader verification responsibility.
- The SHA-256 is computed over exact handoff bytes before launch and used for ledger/environment/dashboard integrity. The worker prompt contract instructs independent inspection and revalidation, but the adapter does not itself re-run `validate_handoff()` inside the worker process; the monitor does independently re-read and digest-check only for display (`handoff.py:137-143`, `agent-config-finalizer.ts:41-44`, `monitor.py:63-83`).
- The MCP runtime is a subprocess bridge: `packages/omo-opencode/src/tools/agentcontrol/mcp-runtime.ts:48-90` passes the action and arguments to Python, with the Python validator and launch ordering remaining authoritative.
