## Flow

- The public native adapter defines `handoff` as a required non-empty string for `Execute`, `Explore`, `Plan`, `Research` (`tools.ts:52-69`, especially line 60), and for `Dispatch` (`tools.ts:110-119`, line 116). Its forwarding path is `createCaller()` → runtime with the unchanged argument object (`tools.ts:39-50`); the focused test proves all five paths preserve the supplied path (`agentcontrol.test.ts:139-166`).
- The Python MCP schema independently requires `handoff` for each direct action (`mcp_server.py:300-335`, required list at 333) and Dispatch (`mcp_server.py:343-370`, required list at 369). `call_tool()` validates before dispatching to either `spawn()` or `dispatch()` (`mcp_server.py:548-564`).
- The public handoff contract is frontmatter plus required Markdown sections. `handoff.py:10-26` defines the 128 KiB limit, schema `agentcontrol-handoff/v1`, ID syntax, six required metadata keys (`schema`, `id`, `action`, `projectRoot`, `sourceRevision`, `status`), and nine required sections. Execute/Dispatch additionally require `Mutation boundary` (`handoff.py:73-90`).
- Validation resolves the launch project and supplied path, requires an existing regular file inside that project, checks size and UTF-8 readability, parses frontmatter, then checks schema, ID, requested-action equality, `status: ready`, and projectRoot before checking sections; it returns canonical path and SHA-256 (`handoff.py:93-143`).
- Rejection happens before creation: `call_tool()` returns the validation error at lines 553-555/560-562 and only calls `spawn`/`dispatch` after a `HandoffMetadata` result. Direct creation itself starts ledger work only later (`mcp_server.py:649-704`); Dispatch does not mark the workflow or insert pending rows until after validation (`mcp_server.py:816-856`). The focused test proves missing handoff yields `HANDOFF_REQUIRED` and zero workers (`test_mcp_v3.py:2143-2152`), while parametrized tests cover empty sections, action mismatch, outside-project paths, and oversize files (`test_mcp_v3.py:2154-2181`).
- A valid direct spawn stores the metadata in the worker ledger row (`mcp_server.py:697-704`), injects `AGENT_CONTROL_HANDOFF_ID`, absolute `AGENT_CONTROL_HANDOFF_PATH`, and `AGENT_CONTROL_HANDOFF_SHA256` into the worker environment (`mcp_server.py:722-737`), and returns the public `{id,path,sha256}` tuple (`mcp_server.py:794-813`). The ledger schema and migration retain all three columns (`ledger.py:52-54`, `84-98`), and insertion binds them (`ledger.py:124-169`).
- Dispatch carries the same validated metadata to every queued item and returns it (`mcp_server.py:847-855`, `872-885`). Its paneless worker launcher reads the persisted columns and re-injects the same three environment variables (`mcp_server.py:906-951`). The propagation tests assert both worker environments and ledger rows (`test_mcp_v3.py:2206-2229`).

## Rejection

- The ordering is structural, not documentary: the only route into launch tools first calls `_validate_handoff`; invalid metadata cannot reach `ledger.add_worker`, `set_workflow_running`, prompt-file creation, or subprocess launch. Path checks reject missing, outside-project, non-file, unreadable, oversized, and invalid UTF-8 inputs (`handoff.py:93-118`).
- Metadata checks reject missing required keys, unsupported schema, invalid IDs, action mismatch, non-ready status, and a projectRoot whose resolved path differs from the launch project (`handoff.py:48-70`, `119-136`). Section checks reject duplicate, missing, or empty required headings (`handoff.py:73-90`).
- `sourceRevision` is required as frontmatter and captured in `HandoffMetadata` (`handoff.py:15`, `36-42`, `137-143`), but the launch ledger/environment/public return deliberately propagate only ID, canonical absolute path, and SHA-256. The worker contract therefore receives a content identity, not a separate source-revision field.
- The injected worker prompt is built only when selected agent plus name, report path, and all three handoff environment values exist (`agent-config-finalizer.ts:16-25`). It identifies the worker kind and embeds JSON runtime metadata (`agent-config-finalizer.ts:26-44`), while explicitly requiring read-first behavior, treating claims as inputs to revalidate, independent authoritative-source inspection, scope/acceptance/mutation/verification adherence, one blocker Report if unreadable, exactly one Report per leader request, a ≤600-character summary, and branch inclusion when applicable (`agent-config-finalizer.ts:41-44`).

## Dashboard

- Each refresh snapshot selects the group’s non-monitor workers, derives state/report timing, loads prompt text, and attaches `handoff_id`, canonical path, launch digest, status, and verified content (`monitor.py:86-147`).
- The monitor verifies the document independently at render-refresh time: it requires an in-project regular file, size ≤128 KiB, UTF-8 decoding, and SHA-256 equality with the ledger’s expected digest; mismatch returns `("changed", "")`, never substituted content (`monitor.py:63-83`).
- The dashboard inspector displays `handoff <id> · <STATUS>` (`monitor.py:409-437`), and the footer exposes `H` for the handoff view (`monitor.py:459-469`). `render_handoff()` shows ID, verification status, SHA-256, absolute path, and the document body with Markdown headings highlighted (`monitor.py:511-545`).
- The per-refresh cache is `handoff_cache: dict[tuple[str, str], tuple[str, str]]`, keyed by `(handoff_path, handoff_sha256)`, populated once and reused for every worker in that snapshot (`monitor.py:103-133`). This gives one read/decode/hash per shared path+digest per refresh, not one per worker.
- Focused dashboard tests verify metadata, `VERIFIED`, body visibility, `H`/full-document rendering, then overwrite the source and assert `changed`, empty content, and absence of substituted text (`test_mcp_v3.py:2232-2260`).

## Risks

- Worker-side enforcement of the digest is prompt/injection based: the adapter requires the three metadata values before injecting the contract (`agent-config-finalizer.ts:16-44`), but this inspected path does not itself re-read/hash the file inside the worker. The monitor independently protects the Dispatch dashboard, while the worker is instructed to read and revalidate.
- The dashboard cache is intentionally scoped to one `snapshot()` call (`monitor.py:103`), so later refreshes re-read and re-hash; within a refresh, workers sharing the same path and digest reuse one result.
- Focused source tests cover schema, ordering, propagation, persistence, dashboard rendering, and substitution defense. The handoff evidence README records the broader run as 132 Python tests and 41 focused TypeScript tests, but this report relies on the authoritative source and focused test assertions above rather than README claims.
