WHAT WAS TESTED
===============

Issue: #4035 - team-mode tmux panes stay stuck on the first message while member
sessions keep running.

Root cause (code): the team tmux layout is fire-and-forget.
- packages/team-core/src/team-layout-tmux/layout.ts:126 (`createTeamLayoutInCallerWindow`)
  types `opencode attach <url> --session <sid> --dir <dir>` into each member pane via a
  single `send-keys ... Enter` at layout creation time.
- After that one send-keys, no code path in the repo ever touches the pane again:
  no liveness check, no refresh, no re-attach. The visible pane output depends entirely
  on the spawned `opencode attach` process keeping its own event subscription healthy
  for the whole team run. If that client-side subscription dies or stalls (attach exit,
  SSE drop, TUI stall, upstream version differences), the pane freezes at whatever was
  last rendered while the member session itself continues unaffected. This matches the
  maintainer triage on the issue ("one-time opencode attach ... no live-tail refresh
  mechanism").

Fix: propagate updates per agent turn, OMO-side.
- New packages/team-core/src/team-layout-tmux/refresh-member-pane.ts:
  reads pane state with one `tmux display-message -p -t <pane>
  '#{@omo_attach_server_url}\t#{@omo_attach_session_id}\t#{pane_dead}\t#{pane_current_command}'`,
  then decides: revive (pane dead, attach exited back to a shell, or empty command ->
  re-send the attach command built from the persisted per-pane options) or redraw
  (alive -> `send-keys C-l`). All failures are log-only; never break the event pipeline.
- New adapter hook packages/omo-opencode/src/hooks/team-session-events/
  team-member-pane-refresher.ts: on `message.updated` / `message.part.updated` for a
  registered team MEMBER session (cheap in-memory team-session-registry gate first),
  loads runtime state, resolves the member's `tmuxPaneId`, debounces 2s per session,
  and calls refreshMemberPane. Wired in src/plugin/event-team-handlers.ts (only when
  team_mode.enabled + tmux_visualization) and dispatched from src/plugin/event.ts.

   OMO-side pane driving (revive/redraw), which works regardless of upstream attach
   behavior.

WHY IT IS ENOUGH
================

- The unit suites pin the exact contract demanded by the issue: given a member pane,
  when update events arrive for the member session (per agent turn), the plugin issues
  pane-targeted tmux commands (revive re-attach or redraw), including debounce,
  non-member/lead/no-pane short-circuits, and log-only failure isolation.
- The event seam is the same one already used by the four existing team-session-event
  handlers; dispatch is null-safe when team mode is off (verified by event.test.ts).
- The live probe documents actual attach streaming behavior on the current opencode
  build, so reviewers can see why the fix does not depend on upstream event delivery.

WHAT WAS OMITTED
================

- No end-to-end tmux reproduction of a full team run: this environment has no tmux
  binary and cannot install one (no root). The repo's own live tmux smoke
  (packages/team-core/src/team-layout-tmux/live-tmux-smoke.test.ts) is opt-in via
  OMO_LIVE_TMUX=1 for the same reason. Pane command construction/quoting is covered by
  unit tests instead.
- No real LLM traffic in the probe: prompts were posted without provider credentials;
  user messages persist and emit message.updated events regardless, which is the event
  class the refresher consumes.
- Sandbox paths under /tmp/opencode/4035-qa* were used with isolated XDG dirs; no real
  ~/.local/share/opencode or ~/.omo state was read or written. No secrets in artifacts.
