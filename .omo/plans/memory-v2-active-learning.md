# memory-v2-active-learning - Work Plan

## TL;DR (For humans)

**What you'll get:** Your coding agent's memory switches from passive to active: it saves what it learns without being asked, reflects on conversations automatically, dreams (deep consolidation + skill maintenance) when you go idle or quit, keeps a self-evolving soul it must announce changes to, and builds Honcho-style people cards with a relationship graph — all configured from your omo.jsonc.

**Why this approach:** Everything rides the existing git-backed memory substrate (commit = persistence) so nothing new can corrupt state; background work always runs in detached, sandboxed, deadline-bounded child processes that survive quit.

**What it will NOT do:** No vector database or embeddings; no multi-observer server machinery; no cron daemon (dreaming triggers on idle/quit/manual, not wall-clock).

**Effort:** Large
**Risk:** Medium - many always-on defaults flip at once; mitigated by per-feature kill switches and storm-safe reservation machinery.
**Decisions to sanity-check:** reflection auto-runs every 25 steps by default; fact extraction always uses the cheap model; dreaming defaults to launching when you quit or idle 30 minutes.

Run lifecycle — ONE canonical state machine for all three kinds (reflection, dream, facts), with three writer ROLES and two sentinels (parent, supervisor, finalizer each own disjoint fields; only the supervisor writes `outcome.json` and only the finalizer writes `final.json`):
1. PARENT creates `<runDir>`, writes `ledger.json` WITHOUT identity, writes `launch.json`, spawns the detached supervisor.
2. SUPERVISOR (never the model child) writes its own `pid`+`processStart` into `ledger.json`, spawns the real child, enforces the deadline, then atomically writes `outcome.json` (= THE CHILD FINISHED) and unlinks `launch.json`.
3. FINALIZER — the live parent, or `session_start` reconcile when the parent died — first CLAIMS the run. SETTLEMENT DIFFERS BY KIND: reflection and dream are reservation-machine runs and settle through `reservation.complete()`; FACTS runs have no reservation at all (`machine.ts:3-31` and `reservation.ts:38-48,88-127` are reflection-only — IC-9 and todo 9 give facts a ledger-based single-flight instead), so a facts run settles by deleting its queue entries and advancing the consumed cursor. Everything else in this lifecycle is shared. The claim step: it acquires an identity-scoped per-run finalization lock (`runtime/locks/finalize-<runId>.lock`, same `acquireLock` record discipline as the other domains) and, holding it, re-checks BOTH `final.json` AND `abandoned.json`; if EITHER sentinel already exists it releases and does nothing. Checking `abandoned.json` is mandatory because todo 13's UNKNOWN-liveness path clears the reservation WITHOUT going through `reservation.complete()` (`packages/memory-core/src/reflection/reservation.ts:107-127`), so the inactive-reservation settlement probe would otherwise read an abandoned run as fully settled and publish `final.json` over it. Only the claim holder proceeds, and finalization resumes from OBSERVABLE PROBES, not from a marker alone. A `finalizePhase` hint (`validated`/`integrated`/`settled`) is written to `ledger.json` as a fast path, but it is NEVER authoritative: a marker written BEFORE its operation cannot distinguish "not started" from "finished but the next write was lost", and one written AFTER cannot distinguish "not started" from "finished but the marker was lost". The claim holder therefore DERIVES the true phase by probing the world, in this order:
   1. INTEGRATED? Every commit created by this plan's OWN auto-integration carries a durable receipt trailer — those reflection/dream merges add `Omo-Run: <runId>` (external `mergePolicy: "integration"` merges are exempt per **IC-9** and use validated-tip ancestry as their authoritative probe) (mirroring the facts `Omo-Facts-Batch: <batchId>`), so the probe is `GitMemoryRepo.log({ range: "<baseSha>..HEAD" })` searching for this run's trailer (**IC-1**). Trailer present = integration already landed; skip it, even though the worktree and branch are gone (`packages/memory-core/src/reflection/worktree.ts:124-148` removes them as part of integrating, so their absence alone proves nothing). Trailer absent AND worktree present = re-run integration from the recorded envelope. A retry must also survive a hard kill DURING `git merge`, which can leave `MERGE_HEAD`, staged changes, or a dirty parent — in that state `assertNoUnrelatedChanges`/`cleanCheck` reject every later memory write (`packages/memory-core/src/git/repo.ts:101-105`) and the integration path would report `parent_dirty` or `merge_conflict` forever, wedging the whole identity. Therefore, holding `memory-write`, a retry that finds NEITHER the run trailer NOR validated-tip ancestry MUST first restore the parent before re-merging from `validatedTipSha` — but ONLY against residue this run PROVABLY owns. NEVER BLIND-RESET: memory is USER DATA (persona, notes, people cards, and hand edits made after the crash), and this repository's existing posture is to REFUSE rather than clobber — integration returns `parent_dirty` without mutating (`packages/memory-core/src/reflection/worktree.ts:96-98`) and `cleanCheck` throws `DirtyRepoError` on any dirty state (`packages/memory-core/src/git/repo.ts:119-123`). A bare `git reset --hard HEAD` would silently destroy those edits, so it is FORBIDDEN here. RESIDUE PROOF, in order: (1) if `.git/MERGE_HEAD` exists AND its sha equals the `validatedTipSha` this run recorded, the interrupted merge is provably OURS, so `git merge --abort` is permitted; (2) if `MERGE_HEAD` is absent or names any other sha, the dirt is NOT ours — do NOT reset, do NOT checkout: leave the tree byte-identical, settle the run as `parent_dirty`, and surface it for the user to resolve, exactly as the explicit-integration path already does. `git reset --hard` appears nowhere in this plan's recovery. To make that retry precise, the `validated` checkpoint also persists `validatedTipSha` (the branch tip that passed validation), and integration is SPLIT into merge-then-cleanup: a retry first probes `git merge-base --is-ancestor <validatedTipSha> HEAD` — ancestor means the merge already landed and only cleanup remains — and cleanup itself is idempotent (removing an already-removed worktree or branch is a no-op). This matters because `finalizeReflectionWorktree` performs validation, merge, worktree removal, and branch removal inside ONE operation (`packages/memory-core/src/reflection/worktree.ts:90-121`), leaving no durable branch tip for a naive retry. Trailer absent AND worktree gone is NOT automatically success: `finalizeReflectionWorktree` removes the worktree after a FAILED outcome too — validation failure, merge conflict, dirty tree (`packages/memory-core/src/reflection/worktree.ts:90-121`) — so absence alone would let a crashed failure be reconciled as success and wrongly advance cursors. It is `no_changes` ONLY when the persisted `validatedTipSha === baseSha` (the branch provably produced no commit); with any other or missing `validatedTipSha` the run is terminal FAILED, cursors do not advance, and facts queue entries are retained.
   2. SETTLED? The probe is sound ONLY because `reservation.complete()` finalizes journals/cursors BEFORE writing the cleared active state (`packages/memory-core/src/reflection/reservation.ts:107-127`); that internal order is LOAD-BEARING and MUST NOT be reordered, and the completion record is written idempotently keyed by `runId`. Given it, probe the reservation state directly: if `runId` is no longer the active run, cursors were already finalized and settlement happened — skip the call instead of letting it throw `Reflection run is not active` (`machine.ts:134-142`, reached through `reservation.complete`, `reservation.ts:107-127`).
   3. Then atomically write `final.json` (= THE RUN IS DURABLE) and release.
   Every step is thus idempotent against a crash at ANY instant, including immediately after an operation and before its checkpoint, because the probe reads the effect rather than a promise. Publishing `final.json` is the only repeatable step and repeating it is a no-op. This claim is MANDATORY because finalization is not idempotent: `completeTransition` throws `Reflection run is not active` once another finalizer has cleared the active run (`packages/memory-core/src/reflection/machine.ts:141`, reached through `reservation.complete`), so a live parent and a fresh reconcile session racing on the same run would crash one of them after a partial merge.
QA and F3 gate every behavioral assertion and every completion wait on `final.json` with a bounded `fs.watch`, never by sleeping. `outcome.json` may be observed ONLY as a synchronization signal (to know when to launch the reconciliation session); it is never durability proof, because it lands before integration.

**IC-1 `GitMemoryRepo.log` (new; `packages/memory-core/src/git/repo.ts` today has NO commit-history/log API (it does expose init/cleanCheck/commitWrite/status/head/lsTree/show and worktree helpers)).**
```ts
export interface MemoryCommit {
  readonly sha: string; readonly subject: string; readonly body: string
  readonly authorName: string; readonly authorEmail: string
  readonly committedAt: string            // ISO-8601, %cI
  readonly trailers: Readonly<Record<string, string>>   // parsed "Key: value" lines of body
  readonly paths?: readonly string[]      // present only when includePaths
}
log(options?: { range?: string; paths?: readonly string[]; limit?: number; includePaths?: boolean }): Promise<readonly MemoryCommit[]>
```
Implementation: `git log --format=%x1e%H%x1f%s%x1f%b%x1f%an%x1f%ae%x1f%cI` — the record separator LEADS each record, so trailing output can never be misattributed; split on \x1e, drop the empty head, split each record on \x1f. Paths are NEVER fetched via `--name-only` on the same invocation (it would interleave with the format output); when `includePaths` is set, run one `git diff-tree --no-commit-id --name-only -z -r <sha>` per parsed sha and split on NUL. Newest-first. `range` is passed verbatim (e.g. `abc123..HEAD`); `paths` become `-- <paths>`.

**IC-3 User-turn counting.** A nudge turn is an ACCEPTED, NON-EXTENSION user input, not an agent-run edge: count `input` events with `source !== "extension"` whose correlated `input_disposition` (matched on `inputId`) is `"queued"` or `"started"` — `"handled"` and `"rejected"` are EXCLUDED. A `handled` input returns before any user message is appended (`../senpi/packages/coding-agent/src/core/agent-session.ts:2666-2670`), so counting it at runtime while hydrating from branch user-role messages would make the resumed count LOWER than the `Omo-Turn` already stamped in a commit, yielding a negative or permanently stuck nudge (`../senpi/packages/coding-agent/src/core/extensions/types.ts:1094-1117`). `agent_settled` is an agent-run lifecycle edge and MUST NOT advance the counter. Hydration MUST NOT reconstruct the count from branch user-role messages: senpi persists extension-submitted prompts as ORDINARY user messages with no source metadata (`../senpi/packages/coding-agent/src/core/agent-session.ts:2805-2814,3323-3328`), so a resumed session would count extension turns, fire premature nudges, and drift from the committed `Omo-Turn`. The accepted-turn counter is therefore DURABLE in its own right: persisted via `appendEntry` (a capability this component already requires, `components/memory/capabilities.ts:3-10`) under the PINNED custom type `omo-memory:accepted-turns` with the schema `{ version: 1, sessionId: string, priorUserTurns: number, sessionBaselineTurns: number }` — senpi accepts arbitrary entry payloads (`../senpi/packages/coding-agent/src/core/extensions/types.ts:1647`), so producer and hydration MUST agree on this exact type and shape or they silently drift — and hydrated from that entry on `session_start`/resume. The resumed baseline likewise comes from that durable record, never from the branch count (a contaminated baseline can exceed the true accepted-turn total and drive the nudge negative or late). For non-authoritative display reference only, the branch view (`readPromptSession` in `components/memory/prompt.ts:70-81` returns `branch.length` today; it gains `priorUserTurns` alongside it). Nudge N = `priorUserTurns - (latest commit with Omo-Writer: memory-tool AND Omo-Session == this session).Omo-Turn`; when this session has no such commit, N = `priorUserTurns - sessionBaselineTurns`, and BOTH values come exclusively from the versioned durable accepted-turn `appendEntry` record — never from the branch count, on a fresh session or a resumed one.

**IC-5 Notice watermark (identity-scoped).** `runtime/notices/soul-head.json` = `{ version: 1, lastNotifiedHead: string }`, scoped to the IDENTITY, not the session — a per-session watermark would silently absorb HEAD on every new session, so a shutdown-launched dream's soul edit would be announced to nobody. ABSENT watermark (first ever compile for this identity) means establish silently: write current HEAD, announce nothing. Thereafter every run compares against this identity watermark and advances it exactly when the notice line is injected. CROSS-SESSION SAFETY: several sessions can be bound to the SAME identity concurrently (`components/memory/index.ts:105-132`), so the read, the delta decision, the notice consumption, and the watermark replacement all happen under an identity-scoped `notice` lock (same `acquireLock` discipline as the other domains) with a compare-and-swap on the previous head; without it two sessions would both emit the notice and both advance the watermark.

**IC-6 Facts queue schema + INDEPENDENT facts cursor.** The journal cursor is reflection-owned: `captureCursorSnapshot` anchors on `reflected_through_message_id`, so until reflection advances, every snapshot re-includes the whole unreflected range (`packages/memory-core/src/journal/cursor.ts:64-98`). Facts therefore keep their OWN per-conversation cursor at `runtime/facts-queue/cursor/<sha256(conversationId).slice(0,12)>.json` (hashed for the same Windows-legality reason as the queue files; the untouched id lives in the payload) = `{ version: 1, enqueued_through_message_id: string | null, enqueued_through_snapshot_line: number, consumed_through_message_id: string | null, consumed_through_snapshot_line: number }`. THE TWO `*_snapshot_line` FIELDS ARE LOAD-BEARING, NOT BOOKKEEPING (this was proven empirically: an implementation that ordered by journal position ALONE regressed the consumed watermark from a newer batch back to an older one, and the regression guard silently passed). Positional comparison in the CURRENT journal entry list is well-defined only when BOTH endpoints appear in that one list. A batch that finishes LATE carries an entry list that does NOT contain the newer batch's endpoint, so looking that endpoint up returns "not found" and a naive guard reads it as "no newer watermark exists" and rolls backward. `end_snapshot_line` (the journal length at publication) IS comparable across batches, so BOTH watermarks advance only when the incoming batch's `range.end_snapshot_line` is STRICTLY GREATER than the persisted `*_snapshot_line`; a batch that is not strictly greater is recorded as consumed WITHOUT moving the watermark. `consumed.json` likewise persists the `end_snapshot_line` of each consumed batch. Message-id positions remain the intra-batch ordering rule; the snapshot line is the INTER-batch one — TWO watermarks with distinct semantics: the EFFECTIVE enqueue anchor is computed under the queue lock as the maximum of `enqueued_through_message_id` and the RETAINED queue file whose `range.end_message_id` has the GREATEST POSITION in the current journal entry list (positional order exactly as `captureCursorSnapshot` derives ranges, `packages/memory-core/src/journal/cursor.ts:68-97`; message ids are opaque and carry NO lexical ordering), validating that the `end_message_id` position lies STRICTLY BEFORE the `end_snapshot_line` boundary — not that the two are equal: `captureCursorSnapshot` sets `end_snapshot_line` to `entries.length` while `end_message_id` is the LAST CANONICAL entry, so the two differ whenever non-canonical entries trail the last message (`packages/memory-core/src/journal/cursor.ts:80-97`) — this closes the crash window where a queue file landed but the cursor write did not, which would otherwise let the next capture publish a larger overlapping range whose different end id slips past endpoint dedupe; enqueue starts strictly after that effective anchor (so successive settles never re-enqueue an overlapping interval), and `consumed_through_message_id` advances ONLY after the extractor's records are applied and committed. On extractor success ONLY `consumed_through_message_id` advances, to that batch's endpoint; `enqueued_through_message_id` is MONOTONIC and never regresses — it stays at the greatest durably queued endpoint. Children are launched fire-and-forget (`packages/omo-senpi/src/components/memory/identity-runtime.ts:112-116`) while later settles keep publishing queue entries (`packages/omo-senpi/src/components/memory/wiring.ts:179-187`), so an older batch ending at E1 can finish AFTER a newer entry ending at E2 was queued; advancing the enqueue watermark on success would reset it E2 -> E1 and let the next capture republish a range overlapping the retained E2 entry. On failure the enqueue watermark does NOT roll back — it stays at the highest DURABLY QUEUED endpoint and the failed queue entries are RETAINED and relaunched verbatim; rolling it back would let the next settle enqueue an interval that overlaps those retained entries (endpoint-only dedupe cannot catch a partially-overlapping range). `consumed_through_message_id` advances only after verified application. Facts read transcript entries through `TranscriptJournal.readEntries()` and never read or mutate reflection state. Facts start positions are NEVER derived from reflection state. { "scope": "person",  "person": { "name": "...", "aliases": ["..."] }, "text": "...", "date": "YYYY-MM-DD" }

The parent-side validator REJECTS a `scope:"project"` record carrying a `person` field and a `scope:"person"` record missing one, so the child's output convention is unambiguous and a malformed record can never be stored as if it were resolved. `scope: "person"` is permitted ONLY when the child resolved an explicit proper name, a known card alias, or a second-person referent to the primary human; otherwise — and ONLY then — it MUST emit `scope: "project"` with `text` prefixed `person-unresolved: `. The PARENT (or the next session's reconcile) reads the JSONL and applies the WHOLE batch through a new `applyFactsBatch(repo, { batchId, records }, author)` in memory-core: ONE `memory-write` acquisition, all file mutations, exactly ONE commit. Per-record `runMemoryTool` calls are FORBIDDEN here — they commit independently, so a mid-batch crash would re-apply committed project facts and double-increment `n=` reinforcement on retry. EXACTLY-ONCE ACROSS THE COMMIT BOUNDARY: every batch gets a stable `batchId` (uuid v4, minted at extraction launch and recorded in the facts ledger), and the single commit carries the trailer `Omo-Facts-Batch: <batchId>`. `applyFactsBatch` runs `repo.cleanCheck()` first and, on ANY error before the commit, restores BOTH the index and the working tree — `git reset HEAD -- <affected paths>` FIRST, then `git checkout -- <affected paths>` plus removal of files it created — before releasing the lock, and ONLY for residue the run PROVABLY owns. RESTORATION IS PATH-SCOPED AND OWNERSHIP-PROVEN, NEVER REPO-WIDE AND NEVER `reset --hard`: `applyFactsBatch` records, per affected path, the pre-write blob sha and the post-write blob sha it produced. A path is restored ONLY when its CURRENT index/worktree blob sha equals the post-write sha this run produced, proving the residue is ours and untouched since; a created file is removed ONLY when its content still matches what we wrote. If ANY affected path drifted from the recorded hashes, the USER edited it after the crash: leave EVERY path untouched, advance NO watermark, keep the batch queued and retryable, and report `parent_dirty` for that batch. Losing a retry is acceptable; losing a user's memory edit is NOT. This mirrors the repository's existing refuse-rather-than-clobber posture (`packages/memory-core/src/reflection/worktree.ts:96-98`, `packages/memory-core/src/git/repo.ts:119-123`); a worktree-only restore is insufficient because `commitWrite` stages with `git add -A` and `cleanCheck` treats any staged state as dirty (`packages/memory-core/src/git/repo.ts:101-122,204-205`), so a hard kill after staging would otherwise wedge every later retry, so a HANDLED pre-commit error leaves no dirty tree. A hard process kill after staging cannot run that handler and MAY leave the tree or index dirty (`repo.commitWrite` stages before committing and has no rollback transaction, `packages/memory-core/src/git/repo.ts:106-122`), so reconciliation ALWAYS restores the tree before retrying. EXTRACTION VALIDATION FIRST: `extraction.jsonl` comes from an untrusted model child, so EVERY line is schema-validated before anything is applied (fail-closed, exactly as the journal store validates its own rows, `packages/memory-core/src/journal/store.ts:214-229`); a single malformed or schema-invalid record FAILS the batch, RETAINS its queue entries, and advances no watermark — malformed output must never be mistaken for an empty one. EMPTY-EXTRACTION TERMINAL PATH: an extraction whose lines all validate and yield ZERO applicable records is a SUCCESS, not a retry — `commitWrite` rejects both an empty pathspec and a no-effective-change batch with `NoEffectiveChangesError` (`packages/memory-core/src/git/repo.ts:108-122`), so `applyFactsBatch` MUST skip the commit entirely, mark the queued entries consumed, advance the consumed watermark, and write `final.json` with `outcome: "no_facts"`. Its crash branch is symmetric: reconcile finds no `Omo-Facts-Batch` trailer but an `extraction.jsonl` with zero applicable records, and takes the same commit-free terminal path. Without this a fact-free conversation would requeue forever. Queue deletion and the consumed watermark advance after that commit (or after that commit-free terminal), so the only POST-COMMIT crash window is commit-landed/cleanup-missing (the pre-commit hard-kill case is the separate recovery branch described just above) — which reconciliation resolves deterministically and WITHOUT any arbitrary history limit: the ledger's `headBeforeApply` (written under the writer lock immediately before application per **IC-9**; absent means application never started) bounds the search exactly, so reconcile runs `GitMemoryRepo.log({ range: "<headBeforeApply>..HEAD" })` (**IC-1**) for the trailer: FOUND means the batch is already durable, so reconcile performs ONLY queue deletion, consumed-watermark advance, and `final.json`; NOT FOUND means nothing landed, so the batch is re-applied from `extraction.jsonl`. Retry can therefore never duplicate a project bullet or double-increment an `n=` counter — so routing in TypeScript is a pure switch on `scope`, with zero heuristics, and the child needs no git, no worktree, and no writer lock. LOCK WINDOW: `memory-write` is acquired ONCE for the batch application (never during the model run), so a facts extraction can never block in-band memory tools for minutes.

**IC-8 Run supervisor + launch-descriptor protocol (guarantees the sentinel).** Reflection, dream, and facts children are spawned indirectly. LAUNCH MANIFEST: the parent applies the sandbox transform FIRST, then serializes the resulting `ReflectionSpawnArgs` (`worker/spawn.ts:25-32`) to `<runDir>/launch.json` mode 0600 = `{ version: 1, runId, kind: "reflection"|"dream"|"facts", command, args: string[], cwd, env: Record<string,string>, hardDeadlineAt, terminationGraceMs, maxOutputBytes, stdoutPath, stderrPath }`. The manifest carries ONE ABSOLUTE `hardDeadlineAt` (epoch ms), never a relative `deadlineMs`: a relative timer would start only after supervisor startup and `spawn()`, so a parent-persisted deadline could elapse while the child is still legitimately running or inside its termination grace, and reconciliation would destroy a live run. The supervisor derives BOTH its SIGTERM instant (`hardDeadlineAt`) and its SIGKILL instant (`hardDeadlineAt + terminationGraceMs`) from that single absolute value. The parent then spawns detached `node <extension-dist>/memory-run-supervisor.mjs <runDir>`; the supervisor reads `launch.json`, spawns exactly that command (it performs NO sandbox logic of its own — the manifest is already transformed), enforces the absolute `hardDeadlineAt` with the existing SIGTERM→SIGKILL process-group escalation (`worker/spawn.ts:163-176`), SIGKILL firing only if the child is still alive after `terminationGraceMs`, then atomically writes `<runDir>/outcome.json`, UNLINKS `launch.json` (it carries env), and exits. OUTPUT CAPTURE: the manifest also carries `stdoutPath` and `stderrPath` (the existing session-directory log files, `worker/spawn.ts:135-183`); the supervisor opens them exactly as the current direct launcher does, and the parent or reconciler reads BOUNDED TAILS from those files when constructing failure detail, exactly as the runner does today (`worker/runner.ts:144-155`) — `outcome.json` records the exit status, never the output bytes. TWO SENTINELS, distinct meanings: `outcome.json` = the CHILD finished (written by the supervisor); `final.json` = the run was VALIDATED, merged/applied, and the reservation completed (written by whoever finalized — the live parent, or `session_start` reconcile for an orphan). Every QA scenario and F3 watches `final.json`; asserting merged commits off `outcome.json` would race the finalizer. BUILD: `memory-run-supervisor.mjs` is added to the extension build entrypoints alongside the existing `omo.js` / `omo-member.js` / `omo-memory-mcp.js` bundles (`packages/omo-senpi/plugin/scripts/build-extension.mjs:37-42,66-75`) — that build change, and the supervisor artifact itself, are delivered by todo 25 (todos 9 and 13 CONSUME it). IDENTITY HANDSHAKE (race-free): the parent creates `<runDir>` and writes the envelope WITHOUT identity; the SUPERVISOR then writes its OWN `pid` + `processStart` into `ledger.json` atomically as its FIRST act, BEFORE spawning the model child — the parent never has to survive to persist identity, so a parent crash right after spawn cannot orphan an unidentifiable run. A ledger still lacking `pid` at reconcile time is UNKNOWN, NEVER crashed: `spawn()` returns before the supervisor is scheduled (`worker/spawn.ts:154-160`), so a fresh session reconciling inside that window would otherwise destroy a live supervisor that simply has not written yet. Missing identity therefore takes the non-destructive watch-then-recheck path through the persisted deadline. The parent MAY additionally record the pid it observed synchronously from `spawn()` as `supervisorPidObserved` to speed liveness checks, but the authoritative identity remains the supervisor's own first write, and neither writer racing the other can produce a destructive verdict. PLATFORM POLICY: `getProcessStartIdentity` returns null outside linux/darwin/freebsd (`packages/memory-core/src/locks/process-identity.ts:36-41`); when either side is null the liveness verdict is UNKNOWN, and UNKNOWN takes the watch-then-recheck path — never the destructive crashed-run path. DEADLINE: the ledger persists `hardDeadlineAt` AND `terminationGraceMs` alongside `deadlineAt` (the supervisor unlinks `launch.json`, so a reconciler that needed the grace value could not otherwise recover it — it is a separate runtime value with its own default, `worker/spawn.ts:125-136`), and `deadlineAt` is exactly `hardDeadlineAt + terminationGraceMs` — one absolute instant shared by supervisor and reconciler — so reconciliation can never reach a timeout verdict while the child is still inside its legitimate run window or its SIGTERM grace (`worker/spawn.ts:13,163-176`). An LLM child cannot be trusted to write structured JSON, and the parent may be gone — the supervisor is the only component that can guarantee the sentinel. `outcome.json` = `{ version: 1, runId, finishedAt: "<ISO>", childExit: { code: number|null, signal: string|null }, timedOut: boolean }`. GATED CHILD LAUNCH (closes the identity window): the supervisor NEVER spawns the model child directly, because `spawn()` returns a live child before its identity can be made durable (`worker/spawn.ts:154-160`) — an abrupt supervisor death in that gap would leave a running child that no reconciler could identify or terminate. Instead the supervisor spawns the SAME bundle in bootstrap mode (`node memory-run-supervisor.mjs --child-bootstrap <runDir>`) as a new process-group leader, with a pipe on its stdin. The bootstrap process does NOTHING except block reading one line. The supervisor now knows that pid synchronously, durably writes `childPid` + `childProcessStart` to `ledger.json`, and only THEN writes the release byte; the bootstrap wakes and spawns the real model child inside its own group. Consequences, all deterministic: (i) any child that can do work has ALREADY had its identity published, so a recorded-identity-free ledger provably means no working child exists; (ii) if the supervisor dies before releasing, the pipe closes, the bootstrap reads EOF and exits WITHOUT ever starting the model child — no orphan, nothing to clean; (iii) the recorded `childPid` is the group leader, so signalling that group reaches the real child. CHILD CONTAINMENT: the bootstrap and model child share a process group and the supervisor installs `exit`/`SIGTERM`/`SIGINT` handlers that signal it, so a supervisor exiting through any HANDLED path terminates the child. WINDOWS (binding, because CI runs the root suite on `windows-latest` across four job matrices, `.github/workflows/ci.yml:84-85,132-133,172-173,213-214`, and Windows builds are native, `AGENTS.md:396`): POSIX process groups and `SIGTERM`/`SIGKILL` are NOT available, so on `process.platform === "win32"` the supervisor spawns the child with `detached: false` and terminates the whole tree with `taskkill /pid <pid> /T /F` at the SIGKILL instant, and at the SIGTERM instant it first attempts a graceful `child.kill()`. The escalation INSTANTS are unchanged — they come from the same absolute `hardDeadlineAt` and `hardDeadlineAt + terminationGraceMs`, so deadline enforcement is platform-independent even though the signalling mechanism is not. A supervisor that cannot contain its tree on this platform is a defect, not an accepted degradation. BOOTSTRAP SELF-ENFORCEMENT (binding, and the reason deadline enforcement is genuinely platform-independent): the SUPERVISOR is not the only deadline enforcer. The bootstrap reads `hardDeadlineAt` and `terminationGraceMs` from the same launch manifest it was handed and arms its OWN timers against those ABSOLUTE instants, terminating itself and its model child at the SIGTERM instant and hard-killing at `hardDeadlineAt + terminationGraceMs`. This closes the abrupt-supervisor-death hole: on ANY platform, a supervisor killed after release leaves a child that still self-terminates at exactly the persisted deadline, so no run outlives `deadlineAt` even though reconciliation reaches it later. It is what makes the win32 UNKNOWN path SAFE rather than merely lossless — `abandoned.json` records that the parent could not verify the child's fate, while the child has already bounded itself. Todo 25 MUST test this directly: kill the supervisor abruptly after release, then assert the child exits by the deadline WITHOUT any supervisor action, on both the POSIX and the injected win32 branch; an ABRUPT death after release leaves an identified live child, which is RECONCILED by todo 13's dead-supervisor/live-child branch; it also records `childPid` + `childProcessStart` in `ledger.json`. Reconciliation MUST check the CHILD identity too and never take the destructive crashed-run path while that child is still alive — removing a worktree underneath a running child would corrupt the run (`packages/memory-core/src/reflection/worktree.ts:139-148`). The SUPERVISOR is the SOLE post-launch writer of `pid`, `processStart`, and `outcome.json`; the parent never persists identity (it may hold the spawned pid in memory purely to await the supervisor inline) and `runReflectionChild` needs NO `onSpawn` hook. The parent no longer waits on the child directly: it waits on the supervisor process (same close semantics), so a live parent still gets its result inline while a dead parent leaves a supervisor that finishes and records the sentinel regardless.
